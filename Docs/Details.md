# Details

[Back to the README](../README.md)

**Blazor.** `Stacks=Blazor` writes a standalone Blazor WebAssembly app (.NET 10) that calls the generated API: a model and an `HttpClient` client per table, a page with grid, search, sort, paging and an add / edit panel (foreign keys as drop-downs), the menu, and the essentials (project file, layout, styles, `.gitignore`). The API allows the app's origin (`DevPort`, default 5190). No tabs or editable child rows yet (a master shows its child tables as read-only grids); the dashboard comes with `Dashboard=true`; `Auth=true` adds the sign-in with the role rules (`WriteRoles`, `ReadRoles`) and `OData=true` the OData clients and pages; see `Docs/TemplateNotes/BLZ_Screens_v1.md`.

**Uno.** `Stacks=Uno` writes a single-project Uno Platform app (.NET 10) that calls generated API: a model and an `HttpClient` client per table and, per table, WinUI 3 list page and add / edit dialog (Uno implements the WinUI 3 API, so the same XAML runs) reading and writing through clients, menu, and essentials (project file with the desktop, browser and Windows heads, entry points, app and main page, `.gitignore`). Desktop head (Skia: Windows, macOS, Linux) only needs the .NET SDK; the browser head needs `dotnet workload install wasm-tools`. The API address is `ApiPort` (or `API_BASE_URL`) and the API allows the browser head's origin (`DevPort`, default 5195). A table with child tables gets the master-detail dialog; `Dashboard=true` adds dashboard, `Auth=true` sign-in page with role rules and guarded columns (`WriteRoles`, `ReadRoles`, `GuardedColumns`), and `OData=true` an OData page per served table. The junction editor is written but not opened from a page, and the pages are the desktop layout; see `Docs/TemplateNotes/UNO_Screens_v1.md`.

**Python.** `Stacks=Python` writes a FastAPI API over SQLAlchemy 2.0 models and Pydantic 2 schemas for SQL Server, PostgreSQL, MySQL or SQLite: the same routes and JSON as the other stacks (so the React, Angular and Blazor apps call it unchanged), validation in the ASP.NET problem form, the junction routes (`PY_Junction`), CSV export and import (`ApiCsv=true`), the change gates and guarded columns (`ApiAuth=true` with `ChangeGates` or `GuardedColumns`: `PY_Gates`), `requirements.txt` and the essentials (engine, error forms, CORS). The password comes from the environment, never a file. See `Docs/TemplateNotes/PY_Routes_v1.md`.

**Rust.** `Stacks=Rust` writes an Axum and sqlx API crate from a PostgreSQL, MySQL or SQLite DB (not SQL Server: sqlx has no driver for it, and a run that names it stops with that reason): a struct, a repository of fixed SQL, the handlers and the validators per table, the module lists and router, and the essentials (`Cargo.toml` with pinned versions, `src/lib.rs`, `src/main.rs`, `src/support.rs`, `.env.example`). It keeps the contract of the other stacks (the same routes, JSON names, status codes, search and clone), so the unchanged React and Angular front ends and the verification scripts work against it. There are no routines in DB: the SQL is written for DB that was read (quotes, placeholders, PostgreSQL's casts for money and enums, `RETURNING` or a second read). The crate is also a library, `FRONTEND_DIR` makes it serve a built front end beside the API on one port, and `RustPort`, `RustCrateName` and `OutputRust` set the port, package name and folder. Compiling it needs a Rust toolchain; `Docs/Verification/Test-RustBuild.ps1` generates, builds and walks one route. The optional `Tauri` essentials group adds `desktop/`, a Tauri 2 shell that runs the API inside the app and shows the built React or Angular front end in a window on Windows, macOS or Linux. Also written: the junction routes (`RS_Junction`), the CSV routes (`ApiCsv=true`, `RS_Csv`), the change gates and guarded columns (`RS_Gates`) and the dashboard. Not written: OData.

**Dashboard.** With `Dashboard=true` a whole-project run also writes a dashboard, derived from what the schema says and not from anything you list: a table's row count, a card for a money column (total, average, largest) and the same sum per foreign key's display name (the ten largest), a count per value of a CHECK-list column or a small lookup table, a monthly trend over a date column, active against inactive rows, rows by start and end dates, a master's count beside its child's, and the latest rows. `DashboardPlan` in Core picks the widgets (at most four cards, two top lists, two breakdowns, two trends and one recent list; a money column called a limit or a rate is not a measure) and every stack renders the same list, so the three front ends show the same page. Each widget is one fixed SQL statement with no parameter, run through EF Core (`SqlQueryRaw`), so it works in either access mode on all four databases; `Dashboard.md` and `DashboardQueries.sql` list the choice and the statements to review before any screen exists. `DashboardMeasures` adds or replaces a widget (`SalesInvoice.TotalAmount:sum:InvoiceDate:month`), `NoDashboardTables` leaves a table out, and `DashboardStrip=true` puts a table's two or three cards above its own grid. The pages draw their own cards, bars and sparkline (no chart package), show every number as text beside the chart and never rely on colour alone. The dashboard is the first menu entry; the aggregates are those of every row, so a project with row-level rules must put `/api/dashboard` behind the same policy as the tables.

**Access mode.** Search, sort, paging, clone and the many-to-many editors reach the database in one of two ways, chosen by the project setting `AccessMode`: `Routines` (default where routines exist: generated code calls procedures or functions the `SP_` templates write) or `Ef` (LINQ over EF Core context; no routine has to be deployed). SQLite always uses `Ef`; any other DB can too, for owners who do not want routines in their DB. A plan in `Ef` mode leaves out the routine templates and adds `CS_SearchQuery`, which holds the filter and the sort that `CS_Repo` and `API_Search` share. The filter matches text ignoring case and treats `%` and `_` in the value as ordinary characters.

**SQLite.** Point the CLI at the file (`--provider Sqlite -d path/to/shop.db`, no server, login or password) and set `DatabaseProvider=Sqlite` and `DatabaseName=<file>` in the project file so the generated project names the SQLite provider and `Data Source=<file>`. A declared type is read the way ORMs read it (`INTEGER` is an `int`, `BIGINT` a `long`, `BOOLEAN`, `DATETIME`, `DECIMAL(10,2)`, `VARCHAR(50)`); an integer named `Is...` or limited to 0 and 1 by a CHECK is a flag; unbounded `TEXT` is long text, as in PostgreSQL, so declare `VARCHAR(n)` for a column that should appear in grids and searches. The generated context stores `decimal` as a double and `DateTimeOffset` and `TimeSpan` as numbers, because SQLite cannot order the forms EF would otherwise use.

Everything else (entities, repos, API, Angular, React, Blazor, WinUI3) is generated from the same model, so the screens look and behave the same whichever database sits underneath. The sample apps in the sibling repos reuse one React or Angular front end over any of the APIs.

**Names.** PostgreSQL and MySQL DBs usually use `snake_case`. Set `NamingStyle=Pascal` in the project file (or `--naming Pascal`) and the generated C# and TypeScript say `CustomerItem` / `CustomerId` while the SQL text and the `[Table]` / `[Column]` attributes keep the real names. MySQL on Windows stores table names in lower case (`lower_case_table_names=1`), so use `snake_case` table names there.

**Passwords.** App and CLI take the password from the connection dialog or `-P`; never commit one. For your own samples, read it from an environment variable (`PGPASSWORD`, `MYSQL_PWD`) at start-up.

**Junction tables and DbSet names.** A table with a composite primary key (a junction table) gets an entity (`CS_Entity` writes its key columns without `[Key]`), a `DbSet`, and `HasKey` in the generated `OnModelCreating`, which calls a partial `OnModelCreatingPartial` that a hand-written part of the context can implement. The `DbSet` properties are named like their tables; `DbSetNames=Plural` in the project file names them in the plural (`Customers`).

**Security.** What the generated SQL does with text from a person (parameters, escaped search patterns, the fixed sort list) and how it is checked: [Security.md](Security.md).

**Template notes.** Each template starts with a short summary (what it generates, its restrictions, what it needs); the long design notes for each one are in [TemplateNotes](TemplateNotes).

**PostgreSQL arrays, intervals, ranges and shapes.** These columns are text to every generated stack, in PostgreSQL's own notation: `{a,b}` for an array of text, whole numbers, numbers, flags (`t`, `f`), ids or dates, `1 day 02:03:04` for an interval (days, hours, minutes and seconds; not months or years), `[1,5)` for a range of whole numbers, numbers or dates, and `(1,2)`, `[(1,1),(2,2)]`, `(2,2),(1,1)`, `<(0,0),1>`, `((0,0),(0,1),(1,1))` for the built-in point, line segment, box, circle and polygon (also line and path). A form shows a text box and the validators refuse a value that does not have the notation (a message names the notation). The database is told the real type: the C# context converts the text to the type Npgsql writes (`CS_DbContext`, or the table's configuration with `EfConfigurations`, carries the converters in a small `PgText` class), the PostgreSQL functions cast it (`NULLIF(btrim(p), '')::int4[]`, so a blank is NULL, or an empty array for an array column that cannot be NULL), and the Rust and Python stacks read the column as text and cast what they write. The column is searched and sorted by its text. A value is kept as the database writes it back (`[1,5]` of whole numbers reads `[1,6)`).

**MySQL sets, wide bits, years, small integers and spatial columns.** A `set('a','b')` column is text of its members separated by commas and no spaces (`a,b`), which is how MySQL reads and writes it; a form shows a text box and the validators refuse a member the set does not have (no member at all is an empty set, a value, even when the column cannot be NULL). A `bit(2)` to `bit(64)` column is the whole number its bits make (a bigint, or a decimal of 20 digits for 64 bits), limited to what its width can hold; `bit(1)` stays a flag. A `year` is a small number limited to 1901 to 2155. A signed `tinyint`, a `smallint unsigned`, a `mediumint` and an `int unsigned` are wider integers in the generated code, so each keeps the limits of its own type. A spatial column (`point`, `linestring`, `polygon`, the multi types, `geometry`, `geometrycollection`) is text in well-known text, `POINT(1 2)`, longitude first as MySQL stores it whatever the column's spatial reference system says about the axis order, in two dimensions; the validators check the shape and the keyword (capitals). The database is told the real type: the C# context converts the text to MySQL's binary form with the column's spatial reference system (a `MySqlSpatial` class at the end of the context file), the stored routines and the Rust and Python stacks use `ST_GeomFromText` and `ST_AsText` with `'axis-order=long-lat'`. A spatial column is not searched or sorted by.

**Types with no mapping.** A column of a type CodeGenNew has no mapping for (PostGIS `geometry` and `geography`, a range of timestamps, a multirange, an array of another element type, `inet`, `hstore`) cannot be used by an EF Core context, so the CLI warns about it (`Warning: column t.c has the type ..., which CodeGenNew does not map`) and the project setting `IgnoredColumns=Tags,Place.Location` (a column name for every table, or `Table.Column`; database name or generated name; a primary key is never left out) leaves it out so the rest of the table generates. A PostgreSQL `numeric` without a precision reads as 38 digits with 4 places (the SQL keeps `numeric` and the entity writes no `[Precision]`), and a money-named one is shown with 2.

**Provider wiring.** `CS_DbContext` and `API_Registration` write the `DbContext` and the API registration for database that was read, so a web API's `Program.cs` is `AddGeneratedDbContext(...)` and `RegisterGeneratedApis()`; the NuGet package the provider needs is named in the generated context's comment (`Npgsql.EntityFrameworkCore.PostgreSQL`, `MySql.EntityFrameworkCore`, `Microsoft.EntityFrameworkCore.SqlServer`).

**Drop-downs for listed values.** A MySQL `enum('a','b')` column is a drop-down of its values on every screen (Angular and React `<select>`, WinUI3 `ComboBox`); a `set` stays a text box. PostgreSQL does the same for a native enum type (`CREATE TYPE status AS ENUM (...)`) and for a text column limited by a single-column CHECK list (`CHECK (priority IN ('Low','High'))`). An enum column needs one extra step: EF Core sends text, which PostgreSQL will not store in an enum column, so run the `SP_EnumCasts` script (a whole-DB template; it creates assignment casts from text and from varchar to each enum type, and a value that is not one of the labels is still refused). **Still open.** Views (tables only), and a CHECK that is not a plain list (a range, an OR).
