# API_RowShapes_v1 and the TreeTables, ContentTables, AssetTables, SoftDeleteTables and EffectiveDatedTables settings

Three table shapes that an ordinary list-and-edit API gets wrong: a table that refers to itself (a tree), a table whose rows are flagged instead of removed (soft delete), and a table whose rows are valid for a period (effective dating). The rules are `TreePlan`, `SoftDeletePlan` and `EffectiveDatePlan` in Core (`RowShapePlans.cs`); `RowShapeWriter` writes the C#. The tree, soft delete and effective dating are also written for the Python and Rust APIs (see below), and so are the content tables. All three need the ASP.NET API and `AccessMode=Ef`, a single whole-number key, and they are off until the project lists the table. A table can have more than one shape (a category tree with soft delete); the user table cannot have any.

`API_RowShapes` writes `Apis/RowShapes.cs`: per table a static `<Table>Shape` class and `RowShapeApi.Register`, called by `API_Registration`. The table's own API (`API_Crud`) overrides `BeforeSaveAsync` and `BeforeDeleteAsync` to call `CheckSaveAsync` and `CheckDeleteAsync`. Those hooks used to exist only with `ApiAuth`; the `CrudApi` essentials now write them also for a project that lists a shape, so **refresh the CrudApi essentials** (the essentials replace option) in an existing project. With `ApiAuth` the extra routes need a signed-in caller, and `deleted` and `restore` need the administrator role.

## TreeTables=Category:ParentCategoryId:3

A table, optionally its parent column (default: the table's one foreign key to its own key) and optionally the deepest level allowed (a root is level 1; blank: no limit). The parent column must allow NULL.

| What | How |
|---|---|
| A parent that is the row itself, or one of its own descendants | 400, `/problems/tree-cycle`. The check walks up from the new parent, so it also stops a cycle that is already stored. |
| A level past the limit | 400, `/problems/tree-too-deep`. The row's level plus the height of the subtree under it, so moving a branch cannot push its leaves past the limit. |
| Delete of a row with children | 409, `/problems/tree-has-children`. |
| `POST {id}/promote-children` | The children become children of the row's own parent (roots when it is a root); the row stays, so it can be deleted next. 404 for a missing row, otherwise `{ moved }`. |
| `GET tree` | Every row depth first, children after their parent and by name (the `Name` or `Title` column, else the key): `{ id, parentId, depth, hasChildren, text }`. Only a row with no parent is a root: a row whose parent is soft deleted is left out with the rest of its branch. |

## ContentTables=Post or Post:Title:Slug:Status:PublishedOn

Posts, pages and articles. A table, then the title (the text the slug is made from), the slug, the status and the published-on columns; each defaults to the column of that name (the title also to `Name` or `Headline`, the stamp also to `PublishedAt`). The slug and the status are text columns that cannot be NULL (the status needs room for `published`, the slug for 14 characters), the published-on column is a date and time that allows NULL and is optional. The rules are `ContentPlan` and `ContentWords` in Core; the text is `RowShapeWriter`.

| What | How |
|---|---|
| The slug | Made from the title when the slug is blank on create: lower case, accents dropped, letters and digits with single hyphens, cut to the column's length. A made slug that is taken gets `-2`, `-3`. A slug the caller sends is made into the same form and refused when taken: 409, `/problems/content-slug-taken`. |
| A new title | Does not move the slug: an update with a blank or an unchanged slug keeps the stored one. A different slug is a rename on purpose and is checked like a new one. |
| The status | Owned by the routes: a new row is `draft` whatever it says, and a save puts back the stored status and published time. |
| `POST {id}/publish` | Status `published`; the published time is stamped the first time and kept after that. Answers the row; 404 for a missing row; doing it again changes nothing. |
| `POST {id}/unpublish` | Back to `draft`. |
| `POST {id}/archive` | Status `archived`. |
| `GET public` | The published rows, the newest published first, `?pageNumber=&pageSize=` (20 by default, at most 100). No sign-in (`AllowAnonymous` with `ApiAuth`). |
| `GET public/{slug}` | One published row; a draft or an archived row is 404. No sign-in. |

The public routes answer every column of the table unless `ContentPublicColumns=Post:Title+Slug+Body+PublishedOn` names the columns to answer (a row of anonymous objects, so a private column such as an author's note never leaves the server; the slug is always in the answer). The slug is unique among the rows the context can see; give the column a unique index too: without one two requests at once can still store the same slug, and the generator says so in its warnings. With the index the second one is refused by the database. Not built yet: a publish that needs a second person, a body editor and full-text search.

**Python and Rust.** Both write the same rules into the table's own router (`PythonContentWriter`, `RustContentWriter`; the words are `ContentWords` and `ContentApiWords`): the same routes, problem type and sentences as the table above. With `ApiAuth` the two public reads are left out of the sign-in check: Python lists the table's `public_router` in `routes.public_routers` (`PY_Mod`; `main.py` includes it first), Rust merges `routes::public_router()` after the sign-in layer (`RS_Mod`, `main.rs`). The Rust crate gets `unicode-normalization` for the accents. A tenant-owned content table and a table also in `RowApprovals` stop the run with a sentence for these two APIs. `Docs/Verification/Tools/content_check.py` plays the rules against a running API.

**A tenant-owned content table** (`TenantTable` with the tenant column on the table) needs `TenantHostColumn`: the anonymous public routes have no signed-in tenant, so they answer the rows of the tenant the request host names (`acme.example.com` is the tenant whose host column is `acme`; `TenantHost.FindAsync`, the rule that already refuses a token on another tenant's host). A host that names no tenant (`localhost`, an address) answers an empty list and a 404, never another tenant's rows. The public query ignores the context's filters and asks for that tenant itself, and for `!IsDeleted` when the table is also in `SoftDeleteTables`. Without `TenantHostColumn` the generator stops with a sentence that says to set it or to list the table in `NoTenantTables`. Everything with a caller stays in the caller's tenant through the context's filter: the save rules, publish, unpublish and archive (another tenant's row is a 404), and the slug check, so a slug is unique per tenant and two tenants may both have `welcome`. Give the table a unique index on the tenant column and the slug. The browser must reach the API on the tenant's host name (the public pages of a front end served from another host name read the tenant of that host). The generated tests of the table do not read the public routes (the test tenant has no host name); `TenantBypassApiTests` plays two tenants with host names: the same slug in both, a rival's publish is a 404, each host answers its own row, a host that names no tenant answers none. `Docs/Verification/Tools/Matrix/tenant_content.settings` is the matrix.

**Publishing that needs a second person.** A table that is in `ContentTables` and also in `RowApprovals` (see `API_Approvals_v1.md`) is not published by `POST {id}/publish`: the route asks for approval, the same request as `POST {id}/request`, and answers the row with the state `pending`. The approval publishes the row (the first time with its published time), a rejection or a withdrawal makes it a draft again, and the requester cannot approve their own request (403, the four eyes of the approvals). A pending row is not public. A refusal of the request is the answer: 403 `approval-requester-unknown` for a person who is not a row of the user table, 409 `approval-wrong-state` while a request already waits, and the project's own `ApprovalHooks.Validate`. Unpublish and archive need no approval, and end a request that still waits for the row (it is withdrawn), so a late approval changes nothing. A request made on the approvals page or from the row's Approval panel works the same way. The state is kept in the table's own status column (`pending` fits any column that holds `published`); `MarkPendingAsync`, `PublishPendingAsync` and `RevertPendingAsync` of the table's `Shape` class (the WinUI3 app: `<Table>Content`, written from the same `ContentRulesWriter` text) are what the approval routes call, in the decision's transaction. The screens show the state in the Status column and offer no Publish on a pending row. The WinUI3 app, which reads the database itself, asks through its in-process `ApprovalService`; the Uno app calls the API. `API_TestContentApprovals` writes `<Table>ApprovalPublishApiTests.cs` (the request, the four eyes, the approval, a rejection, an archive that ends the request, a stranger) over the people and the row that `ApprovalTestSeed` puts in the scratch database; the WinUI3 `ApprovalServiceTests` have the same cases in process. Not covered: the Python and Rust APIs (no content tables there yet).

**Screens.** The list page of every front end (React, Angular, Blazor, Uno, WinUI3) shows Publish, Unpublish and Archive on a row, each only when it would change something (Publish for a draft or an archived row, Unpublish for a published one, Archive for any row that is not archived). In the form the status and the published time are text, not boxes, and the slug box is not required and says it is made from the title when left blank (a placeholder on the web). `ContentScreens` in Core holds the captions, the failure sentences and the tests of a row's state; `FormColumn` makes the status and the published time system-stamp fields and the slug not required, so every stack's required check follows. The web pages and the Uno app call the API (`publish`, `unpublish` and `archive` on the client). The WinUI3 app reads the database itself, so it makes the same guarded UPDATE (`ContentScreens.SetCalls`) and runs the same slug and status rules before a save: `WinUI3_Content` writes `Repositories/Content.cs` with a `<Table>Content` class whose `MakeSlug` and `PrepareAsync` are the text the API writes too (`ContentRulesWriter`). The OData pages and the pages of a table with children have them too: an OData page publishes through the REST client and always asks for the status, even when the person hides its column. The edit dialog of a saved row has the same buttons (a new row has none): a click changes the state on the server and the dialog shows the new status and published time while the other fields keep what was typed, so a save afterwards still writes the typed values. The desktop dialogs show the slug box with the hint "Leave blank to make it from the title" as well.

## AssetTables=Asset or Asset:StorageKey:FileName:MimeType:Size:Url

A table whose rows point at a stored file: the row holds the key in the store, the name the file had, its type and its size, never the bytes. A table, then the columns of the storage key, the file name, the file type, the size in bytes and the optional download address; each defaults to the column of that name (`StorageKey`, `FileName`, `MimeType`, `SizeBytes`). The key column cannot be NULL and needs room for 44 characters, the name column cannot be NULL, the size is a whole number, and every other column must allow NULL or have a default, because the upload route fills only these. The rules are `AssetPlan` and `AssetWords` in Core; the text is `RowShapeWriter`. A table also in `SoftDeleteTables`, `OwnedTables` or the tenant table stops the run with a sentence.

| What | How |
|---|---|
| `POST upload` | A multipart form with a field named `file` (the first file when none has that name). The file is written to the store under a key the server makes (32 hex digits and the lower case extension), then the row is added; if the row cannot be saved the file is removed again. Answers 201 and the row, with the download address in the `Url` column when there is one. |
| No file in the form, or an empty one | 400, `/problems/asset-no-file`. |
| A file over `AssetMaxBytes` (default 10485760) | 413, `/problems/asset-too-large`. |
| A type not in `AssetAllowedTypes` (`image/*,application/pdf`; empty for any) | 415, `/problems/asset-type-not-allowed`. The type is the one the client sent, lower case and without parameters. |
| `GET {id}/download` | The file with the row's type and name as a download (`Content-Disposition: attachment`, `nosniff`), range requests allowed. 404 for a missing row, 404 `/problems/asset-file-missing` when the store has no file for the row. Needs a sign-in with `ApiAuth`. |
| A delete | The row is deleted and then the file is removed from the store (`AfterDeleteAsync`, a new hook of the CRUD base: refresh the `CrudApi` essentials in an existing project). A delete the database refuses (a row that others refer to) keeps the file. A key with no file behind it is not an error. |
| The ordinary create and update routes | The storage key cannot be named by a request. A row made by the ordinary create holds an unattached key (`unattached-` and a guid) and has no file; an update keeps the stored key, type and size and may change the name and the other columns. |

The store is `IAssetStore` (`SaveAsync`, `OpenAsync`, `DeleteAsync`). The default `LocalFolderAssetStore` keeps one file per key in `AssetStoreFolder` (default `App_Data/assets`, relative to the folder the API runs in) and refuses a key that could leave the folder. To keep files in S3 or Azure Blob, register your own `IAssetStore` as a singleton; `RowShapeApi.Register` hands the routes the application's services. Several asset tables share the store and the limits.

**The insert.** The upload writes the four columns it knows (key, name, type, size) with one INSERT and reads the new key back (`OUTPUT INSERTED` on SQL Server, `RETURNING` on PostgreSQL and SQLite, `LAST_INSERT_ID()` on MySQL), so the database fills every other column with its default; an entity would send the CLR default of each (a `datetime` column got 0001-01-01 and SQL Server refused it).

**Python and Rust.** Both write the same routes, sentences and problem types (`PythonAssetWriter`, `RustAssetWriter`; the words are `AssetWords`) into one file for the database, `app/routes/asset_files.py` and `src/routes/asset_files.rs` (`PY_Assets`, `RS_Assets`), and `PY_Mod` and `RS_Mod` list it before the tables' routers. The store is `AssetStore` (`LocalFolderAssetStore`; `ASSET_STORE_FOLDER` or `AssetStoreFolder`): Python's `use_store()` swaps it, Rust's `use_store()` must be called before the first request. Python keeps the storage key out of a request's hands with SQLAlchemy events on the table's class (an ordinary insert gets an unattached key, an update restores the stored key, type and size, a delete removes the file once it commits); Rust has no events, so `RS_Routes` adds the same three steps to the table's own create, update and delete. `requirements.txt` gets `python-multipart` and `Cargo.toml` gets axum's `multipart` feature. The tests are `tests/test_assets.py` (`PythonTests=true`, `PY_TestAssets`) and `tests/api/asset_routes.rs` (`RustTests=true`, `RS_TestAssets`); both put the files in a temporary folder.

**Screens.** The list page of every front end (React, Angular, Blazor, Uno, WinUI3, and the OData pages that are the same templates) has an Upload control in its bar and a Download button on a row; no binary column is ever shown. `AssetScreens` in Core holds the captions, the failure sentences (`Problem while uploading!`, `Problem while downloading!`) and the `accept` list of the file box (`AssetAllowedTypes`). In the form the storage key, the file type and the download address are text, not boxes, because the upload owns them (`FormColumn` makes them system-stamp fields); the size stays a number box that the server ignores.

| Front end | Upload | Download | The client behind it |
|---|---|---|---|
| React | a hidden file input behind an Upload button | `Download` saves the blob | `uploadFile` and `downloadFile` in `api/client.ts` (essentials: refresh them in an existing project), `upload` and `download` in the table's api module |
| Angular | the same, with a template reference | the same | `upload` and `download` of the table's service (`FormData`, a blob answer, the name from `Content-Disposition`) |
| Blazor | an `InputFile` in a label (the file is read up to `AssetMaxBytes`) | `DownloadAsync` hands the bytes to `codegenSaveFile`, a script `wwwroot/index.html` defines (essentials: refresh it) | `UploadAsync(Stream, name, type)` and `DownloadAsync(id)` of the table's client (`ApiClientCode`, shared with Uno) |
| Uno | a `FileOpenPicker` (attached to the window on the Windows head through `App.MainWindow`, a new member of `App.xaml.cs`: refresh the essentials) | a `FileSavePicker` and `FileIO.WriteBytesAsync` | the same client |
| WinUI3 | a `FileOpenPicker`; the app reads the database itself, so `Assets.cs` (`WinUI3_Assets`) holds the store and `<Table>Assets.UploadAsync` copies the file into the store and adds the row | a `FileSavePicker`; `ExportAsync` copies the stored file there | none: the dialogs call `<Table>Assets.PrepareAsync` before a save, and a delete reads the key first (`RememberFileAsync`) and removes the file after (`AfterDeleteAsync`) |

**The edit dialog** has the same two buttons and a picture. A new row's dialog has an Upload button: the file makes the row (the storage key, name, type and size come from the server). React, Angular and Blazor go on editing the saved row, so a caption can be typed and saved; WinUI3 and Uno close the dialog and the list shows the new row. A saved row's dialog has a Download button, and, when the stored type is an image other than SVG, a picture at most `AssetScreens.PictureEdge` pixels wide: React and Angular read the bytes through the client (an image tag cannot send the sign-in token), Blazor puts them in a `data:` address, the desktop apps decode them into a `BitmapImage`. `AssetDialogCode` in Core writes the desktop dialogs' XAML, handlers and view-model members for WinUI3 (through `<Table>Assets.CopyFileAsync`, which reads the store and never the database) and Uno (through the API client). A browser app on another origin reads the downloaded file's name from `Content-Disposition`, so the API's CORS policy (ASP.NET, Python and Rust) exposes that header when the project has an asset table.

Not covered: a table limited to an owner or a tenant; a `varbinary` column; a store other than a local folder (S3 and Azure Blob are the owner's `IAssetStore`). `Docs/Verification/Tools/Schemas/assets.sql` (and `assets_postgres.sql`, `assets_mysql.sql`) is the scratch schema: `python new_scratch_project.py Ast --schema assets --stack api,python,rust --set AssetTables=Asset:StorageKey:FileName:MimeType:SizeBytes:PublicUrl,Document --set ApiTests=true --set PythonTests=true --set RustTests=true`.

## PolymorphicLinks=Attachment:OwnerType:OwnerId:Product|Opportunity|Customer

A link table whose far side is a pair, a record type name and a record id: a brochure attached to a product or an opportunity, a comment or a note on any record. A foreign key cannot hold that, so the checks are code. The table, the type column, the id column and the tables the type may name (at least two, each with a single whole-number key) are the setting; `:remove` after them removes a deleted row's links instead of refusing the delete. The id column has no foreign key; the table may also be an asset table (the brochure is a file).

| Where | Rule |
|---|---|
| Create and update of the link table | The type is trimmed and matched to a listed table without regard to case; no match is a 400 `link-type-unknown` that names the listed tables. The type is written as the table's own name (`product` is saved as `Product`). The id must be a row of that table, else a 400 `link-target-missing`. |
| Delete of a listed table's row | Refused with a 409 `link-target-in-use` while a link table without `:remove` has a row naming it. With `:remove` the links go after the row is gone (`AfterDeleteAsync`). |
| The type column | `PolymorphicPlan.ApplyChoices` gives it the listed names as its choices, so every front end shows a drop-down, the validators name the values and the generated tests take the first. A column that already lists values (a CHECK list) keeps its own. |
| The attachments grid | `PolymorphicPlan` adds a child to each listed table (a `ChildForeignKeyModel` with a `TypeColumn` and a `TypeValue`, kept out of the foreign keys the database declares), so the listed table's screen is a master-detail screen and its edit dialog shows the link table's rows whose id is the row and whose type is the table (React, Angular, Blazor, WinUI3 and Uno read it as any child grid; the web screens filter the whole list, the desktop ones filter in the query). A link table with no screen of its own (too small to get one, or left out of `Screens`) gives no grid. A delete the link table refuses answers 409, which the React pages show as "in use". |

`RowShapeWriter` writes `CheckLinkAsync`, `CheckLinksAsync` and `AfterDeleteAsync` in the table's `<Table>Shape`; Python (`PY_Links`, events on the model classes, `app/routes/link_rules.py`) and Rust (`RS_Links`, `check_*`, `refuse_linked_*` and `remove_links_*` called from the routes, `src/routes/link_rules.rs`) have the same rules and sentences. `Tools/polymorphic_check.py` plays them over HTTP against any of the three over `Tools/Schemas/polymorphic.sql`. The generated generic add, change and remove tests are not written for a link table (a row of it must name a row of another table). Not covered: an "attachments" section on the screen of each listed table, a link table or listed table that is limited to an owner or a tenant, and a listed table with a text key.

## SoftDeleteTables=Customer,Order:IsRemoved

A table and optionally the yes/no column (default `IsDeleted`, NOT NULL). `DeletedOn` (date and time) and `DeletedBy` (text), both allowing NULL, are filled when the table has them; `DeletedBy` is the signed-in name with `ApiAuth`.

- `DELETE` sets the flag instead of removing the row and answers 200; the delete of a row that is already flagged is 404.
- `CS_DbContext` adds `HasQueryFilter(e => !e.IsDeleted)`, so a flagged row is in no list, search, look-up or read of the generated API, and a PUT to it is 404. Regenerate the context. The Python and Rust APIs have their own filter (see below); a WinUI3 or Uno app over the context of its own and reports do not know it.
- `GET deleted` lists up to 500 deleted rows, the last deleted first (an administrator).
- `POST {id}/restore` clears the flag and the stamps and answers the row; 404 when there is no such row, 409 `/problems/not-deleted` when it is not deleted (an administrator).

A row that other rows refer to is not removed by a soft delete, so the foreign keys keep pointing at it; a unique index still counts it.

## DefaultRowTables=CustomerAddress:IsDefault:CustomerId+AddressType

A table of which exactly one row per group is the default (an address of a customer per type). The yes/no column cannot be NULL and the group is made of one or more other columns (`+` between them); the key is a single whole number.

| Rule | How |
|---|---|
| A save with the mark | `CheckDefaultAsync` clears the mark of the others of the group in a transaction that the save of the row commits (`DefaultRows.InSaveTransactionAsync`, committed on `SavedChanges`, rolled back on `SaveChangesFailed` or when the request ends without a save), so a unique index on the group where the flag is set is never broken |
| A save without the mark | a row that is alone in its group, or that was the only default, is marked instead: a group that has rows has a default |
| `POST {id}/make-default` | moves the mark in one transaction; a row that is the default answers 200 and changes nothing; a missing row is 404 |
| A delete of the default row | `CheckDefaultDeleteAsync` hands the mark to the next row of the group (the lowest key) in one transaction before the delete runs |
| Clone | none: a copy of the default row would be a second default (`CloneShape`) |
| The screens | a "Make default" button on every list row that is not the default of its group (`DefaultRowScreens`): React, Angular and Blazor call the route (`makeDefault`, `MakeDefaultAsync`) and read the list again, Uno calls it through its client, WinUI3 moves the mark in one transaction of its own context. The edit dialog of a saved row has the same button, and the flag is text there (`DefaultRowScreens.IsFlagColumn` makes it a system-stamp field): a new row is not given a mark by the form, the API gives the first row of a group the mark, and the WinUI3 dialog, which writes through its own context, does the same before it saves. The default row of a group cannot be moved to another group, on any stack: while its group has other rows (`DefaultRowScreens.LeavesGroupText`), nor into a group that has a default (`GroupTakenText`). The WinUI3 dialog shows the sentence in its error bar (the unique index on the flag would end the app), and the API answers 409 `/problems/default-row-moved` with it (ASP.NET, Python and Rust); React and Angular show the detail of any 409, Blazor and Uno read it. A row that is not the default moves freely and joins the new group without the mark; the only row of a group may move into a group that has no default |

`RowShapeTests` writes two tests (a mark taken, `make-default`). Not served for a table limited to an owner or a tenant. Python (`PythonDefaultWriter`: `settle_default` and `promote_default` called before the commit, so the marks move in the transaction of the save; the helper runs inside `no_autoflush` so the row's own flag is not written before the old mark is cleared) and Rust (`RustDefaultWriter`: `settle_default` before the write; a row that asks for the mark while another row holds it is written without it and `move_default` moves it in one transaction right after) write the same rule and the same route; Rust moves the mark after the write, not in the same transaction, so a failure between the two leaves the old default in place.


## SnapshotColumns=OrderItem:ProductName<-Product.Name+UnitPrice<-Product.Price+TaxRate<-TaxCategory.Rate:LineTotal=Quantity*UnitPrice

A child table that keeps what its parents looked like when the row was written (the order line that copies the product's name, price and tax rate). The copied columns are `Column<-ParentTable.Column` joined by `+`; the optional last part is a line total, `Column=FactorA*FactorB`. The table has exactly one single-column foreign key to each parent it copies from, a copy has the type of its source (a text copy is as long, a source that allows NULL needs a target that does), and the total and its factors are number columns.

| Rule | How |
|---|---|
| Create | `CheckSnapshotAsync` reads the parent row through the foreign key and copies the columns; a parent that is not there is a 400, `/problems/snapshot-parent-missing`; a parent key that may be NULL and is empty copies nothing |
| Update | the stored copies are read back and put on the row, so a value in the body is ignored, and a change of the foreign key does not re-copy |
| Total | `Column = FactorA * FactorB` on every save, in the type of the total |
| The body | a create or update body may leave the copies and the total out (the request schema makes them optional, the Rust struct defaults them) |
| The screens | the forms show the copies and the total as text (`SnapshotPlan.IsOwnedColumn` makes them system-stamp fields); a WinUI3 or Uno dialog shows nothing for them on a new row (`SavedRowVisibility`); the WinUI3 dialog writes through its own context, so `DesktopFormCode.SnapshotCheckLines` does the same copy before it saves, and Uno goes through the API |

Python writes `fill_snapshot` and `SNAPSHOT_OWNED` into the table's router (`PythonSnapshotWriter`) and Rust writes `fill_snapshot` (`RustSnapshotWriter`; a SQLite decimal is a float, so the total is a float there). Those two templates see one table at a time, so `ProjectGenerator` remembers the database for the run (`SnapshotPlan.Remember`); a table generated alone gets the ASP.NET rule only. Not served for a table in LogTables or SingleRowTables. The order that becomes read-only once placed (the status gates) is a separate setting and not part of this one.


## EffectiveDatedTables=Price:ValidFrom:ValidTo:ItemId+CurrencyId

A table, the first and the last day columns (the same date type; the first cannot be NULL, an empty last day is open) and optionally the columns that say what the row is a price of (default: every single-column foreign key). Both ends are inclusive.

- A save whose last day is before its first day: 400, `/problems/effective-range`.
- A save whose period overlaps another row with the same values in the group columns: 409, `/problems/effective-overlap`. A row is never compared with itself, so a change that keeps its own period is fine; a table with no group column is one group.
- `GET current?on=2026-10-27&itemId=5` answers the rows in effect on the day (today when `on` is left out), narrowed by the group columns that are given.
- The table gets no Clone: a copy would have the period of the row it copies.

## Generated tests, the http file and the clients

`API_Test` adds, to the table's own test class, the tests of each shape it has: cycles, delete with children and promote, the tree order and the depth limit; delete, hidden, listed as deleted, restore, restore twice and restore of a missing row; a backwards period, an overlap and a neighbouring period, the rows in effect on the first and last day and the days around them, and an open period. Every test makes its own rows with the sample body and removes them. The ordinary tests of an effective-dated table send periods of one day in the 19th century (before real data, after SQL Server's 1753) with a last day of their own, so they never overlap each other or a period that is open. The test that needs a group with no open period skips when the group has one.

`API_Http` writes the requests of the extra routes. The React, Angular, Blazor and Uno clients get `getTree`, `promoteChildren`, `getDeleted`, `restore` and `getCurrent` (`GetTreeAsync` and so on) for the tables that have the shape.

## Not covered

No tree screen yet: a tree as an indented list with expand and collapse and "add a child" is not written in any front end; the clients only have the calls. Only the tree is written for the Python and Rust APIs (`PythonTreeWriter` and `RustTreeWriter`, inside the table's own router): the cycle and depth checks on create and update, the refusal to delete a row with children, `GET tree` and `POST {id}/promote-children`, with the same problem types and sentences; the Rust tree is left out for a table limited to an owner or a tenant, and the Python tree limits its rows to the caller's tenant. Soft delete is written for them too (`PythonSoftDeleteWriter`; in Rust `RustTable` adds the flag test to every read and update statement of the table, and the repository gets `soft_delete`, `restore`, `deleted` and `exists_any`): the delete flags the row and stamps `DeletedOn` and `DeletedBy` (the caller's name, with sign-in), a flagged row is in no list, search, look-up, read or tree, a second delete is a 404, `GET deleted` and `POST {id}/restore` (administrator only with sign-in; 409 `not-deleted` for a row that is not flagged) list and bring back rows. In Python one listener on the session adds the flag test to every select of the table (the counterpart of the query filter); the deleted list and the restore ask for `include_deleted`. For a table limited to an owner or a tenant the Rust API hides and flags rows but writes no deleted list and no restore, since those would have to be limited too, and the Python API leaves the tenant table itself alone. Effective dating is written for them as well (`PythonEffectiveWriter`, `RustEffectiveWriter`): the backwards-period and overlap checks on create and update (the Python update reads the saved row for the columns the body leaves out; a flagged row is not compared) and `GET current?on=&<group>=`, with the same problem types and sentences. The check that a parent is not a descendant and the overlap check read and then write, so two requests at the same moment can both pass; a unique index or a serializable transaction closes that. Soft delete does not cascade: the children of a soft-deleted tree row stay, and the tree answer leaves them out with their branch (only a row with no parent is a root). A tree cannot have a composite key, and the depth limit is per table.

Checked with `Docs/Verification/Tools/Schemas/row_shapes.sql` (a category tree with soft delete, a soft-delete table and an effective-dated price table): the generated API tests over a SQLite copy, with and without `ApiAuth`, and over the same tables on SQL Server, PostgreSQL and MySQL.

## PartyTables=Party:PartyIdentifier:Scheme:Value

One party row (a customer, a supplier, a carrier or all three) with child rows of identifiers: a scheme (a tax number, a registration number) and a value. The setting names the party table and its identifier table; the scheme and value columns default to `Scheme` and `Value`. Both tables need a single whole-number key, the identifier table exactly one single-column foreign key to the party, and the two columns are text that cannot be NULL.

| Rule | How |
|---|---|
| A save of an identifier | `CheckIdentifierAsync` trims the scheme and the value and refuses a pair another row holds, compared without regard to case (409 `/problems/party-identifier-taken`). The same value under another scheme is a different identifier |
| `GET by-identifier?value=&scheme=` on the party table | the parties that hold an identifier with that value, of that scheme when one is given, lowest key first, at most 50; no value is a 400 |
| Clone of an identifier | none: a copy would repeat the pair (`CloneShape`) |

The check and the save are two steps, so two requests at the same moment can both pass; a unique index on the scheme and the value in the database closes that, and a run warns when the identifier table has none (`PartyPlan.MissingIndexes`). ## RateTables=ExchangeRate:FromCurrency:ToCurrency:Rate:RateDate

A table of exchange rates: what one unit of a currency is worth in another from a day on. The four columns default to `FromCurrency`, `ToCurrency`, `Rate` and `RateDate`. `RatePlan` in Core reads the setting; `RowShapeWriter` writes the C#.

| Rule | How |
|---|---|
| A save of a rate | `CheckRateAsync` writes the currencies trimmed and in upper case, refuses a missing currency or two equal ones and a rate that is not above zero (400 `/problems/rate-invalid`), and refuses a pair another row holds on the same day (409 `/problems/rate-taken`). A date and time column is compared by its day |
| `GET rate?from=&to=&on=` | the latest row of the pair on or before the day (today when none is given); none is a 404 `/problems/rate-missing`; a missing currency or two equal ones is a 400. The opposite pair is its own set of rows unless `RateInverse=true` (below) |

The check and the save are two steps, so two requests at the same moment can both pass; a unique index on the two currencies and the day closes that, and a run warns when the table has none (`RatePlan.MissingIndexes`). The three APIs answer the index's refusal as the rule does: the ASP.NET API tells the index from another unique index of the table by the name the database's message gives (`RatePlan.PairIndexes`, `PartyPlan.RefusalMark`, `RepeatsRate` in `API_EssentialProgram`, which needs the run to have read the database), the Python and Rust APIs by a read after the rollback (`rate_taken`, `rate_refused`). Played with `Docs/Verification/Tools/rate_check.py` over `Schemas/rates.sql` against the ASP.NET, Python and Rust APIs, with `rate_odata_check.py` through the OData routes, with a sign-in by `rate_auth_run.py`, and over SQL Server, PostgreSQL and MySQL by `live_rate_run.py` (with `rate_race_check.py`: many creates of one pair and day at once, and two rows moved to one free day, give one saved and the rule's 409 for the rest). `PY_TestRates` (`tests/test_rates.py`, `PythonTests=true`, not for SQL Server) and `RS_TestRates` (`tests/api/rate_routes.rs`, `RustTests=true`) play the rule and the lookup through the routes, adding rates of a pair of currencies no other run uses and removing them again. They are written when the tests can fill the table (`RateTestPlan`): an identity key, currencies of three characters or more, and no other column that must have a value is a foreign key or in a unique index. The generic update test of the tables (`API_Test`, `RS_Test`) does not change a currency column, since a save writes it in upper case. The shape detector suggests a table with two currency columns, a rate and a day (`Exchange rates`), and the list screens of every front end have a rate lookup. 

**`RateInverse=true`** (ASP.NET, Python and Rust): when the opposite pair has a row on or before the day that is newer than the pair's own (or the pair has none), the lookup answers it with the currencies swapped and the rate as one divided by it, with the header `X-Rate-Inverted: true`; on the same day the pair's own row wins. `FindRateAsync` of the rate table's shape class (`find_rate` in the Python and Rust router) does the lookup for the route and for documents; Python and Rust answer such a row with key 0 (it has no row of its own), which the screens read. The rate column must be a decimal, double or float.

**`RateDocuments=SalesInvoice:CurrencyCode:FxRate:Total:BaseTotal:InvoiceDate` with `BaseCurrency=USD`** (ASP.NET with `AccessMode=Ef`, Python and Rust; `RateDocumentPlan`): a document that keeps the rate it was written with. `ConvertCurrencyAsync` runs in the table's `CheckSaveAsync`, so the REST and OData routes both use it. The currency is written trimmed and in upper case (blank: 400 `rate-invalid`); the rate is the one in force on the date column (today without one) from the first table of `RateTables` (or the table named in the seventh part, `...:InvoiceDate:CardRate:EUR`), 1 for the base currency (`BaseCurrency`, or the eighth part for that table), and 400 `/problems/rate-needed` when there is none; an update keeps the stored rate while the currency and the day stay the same, so a rate added later changes nothing already written; the converted amount is the amount times the rate, rounded to the converted column's scale (2 when it has none). The rate and the converted amount are the server's: what the caller sends in them is overwritten. The Python router writes `convert_currency` (`PythonRateDocumentWriter`) and the Rust router `convert_currency` (`RustRateDocumentWriter`), called before the commit; an update there ignores the rate and converted amount of the body. With `Decimal` columns the amount is rounded half away from zero as `Decimal`; with floating point columns (Rust over SQLite has no `rust_decimal`) it is multiplied and rounded as `f64`. The screens show the rate and the converted amount as text. The WinUI3 dialog writes through its own context, so `RateScreens.WinUI3DocumentCheck` (written into `SaveAsync` by `WinUI3_DetailScreen` and `WinUI3_DetailMasterScreen`) does the same conversion before it saves, over the rate table of its own context with the inverse, and a refusal shows in the dialog. Uno goes through the API: `ApiException.Sentence` and `RateRefusalAsync` of `UNO_EssentialSupport` (written when `RateTables` is set; an essentials file, so an older project keeps its copy) keep the detail of a `/problems/rate-` 400 or 409, and `Explain` gives it back instead of "Some of the values are not acceptable!". Clicked through in WinUI3 and Uno (Windows target) with `winui3_rate_document_check.ps1`.

**`PriceListTables=PriceListItem:PriceListId:ItemId:MinQuantity:Price:PriceList[:CurrencyCode[:ValidFrom[:ValidTo[:CustomerGroup]]]]`** (ASP.NET with `AccessMode=Ef`, Python and Rust; `PriceListPlan`, `PriceListWriter`, `PythonPriceWriter`, `RustPriceWriter`): price rows with a minimum quantity, in lists that have a currency, a period and an optional customer group. The five names of the price table default to `PriceListId`, `ItemId`, `MinQuantity`, `Price` and `PriceList`; on the list table the currency, first day and last day default to `CurrencyCode`, `ValidFrom` and `ValidTo` (date columns without a time, the last day may be NULL for an open end), and the group is used only when the entry names it. `CheckPriceAsync` runs in the table's `CheckSaveAsync` (`check_price` in the Python router, `check_price` in the Rust one): a minimum quantity that is not above zero or a negative price is a 400 `/problems/price-invalid`, and another row of the same list that holds a price for the item from the same quantity is a 409 `/problems/price-taken`. `GET price?item=&quantity=&on=&currency=[&group=]` answers the row in force: among the lists of the currency that are valid on the day (today without one; the first and the last day count) the row of the item with the largest minimum quantity not above the quantity (1 without one). With a group the lists of that group are read first and the lists with no group are the fallback; without one only the lists with no group are read. No price is a 404 `/problems/price-missing`; a missing item or currency, or a quantity that is not above zero, is a 400. The currency and the group are read in any case. The list table is added to `EffectiveDatedTables` with the currency (and the group) as its group columns, so two lists of one currency and group cannot overlap in time (409 `effective-overlap`). As for the rates, the check and the save are two steps: a unique index on the list, the item and the minimum quantity closes the gap, a run warns when it is missing (`PriceListPlan.MissingIndexes`), and the APIs answer its refusal as the rule does (`PriceListPlan.PairIndexes`, `RepeatsPrice`; `price_taken` and `price_refused` in Python and Rust). The minimum quantities are compared in memory as decimals in the ASP.NET code. A price table may be limited to an owner (`OwnedTables`, on the table or through its list) or a tenant: the lookup reads only the caller's rows (the owner scope of `IOwnerScope` in ASP.NET, the repository's scoped read in Rust, `only_owned` and the tenant filter in Python, the tenant filter of the context for a tenant in ASP.NET), and a row of a tenant may name only a list of that tenant (400 `price-invalid`). The list table may be limited the same way, and then the price table must be too. The periods of an owner's lists with an owner column of their own are kept apart per owner (the owner column is added to the group columns of the implied `EffectiveDatedTables` item), a tenant's per tenant (the tenant filter in ASP.NET and Python, the tenant as a group in Rust); a list owned only through a parent has no period rule. A price row with an owner column of its own may name only a list of the same owner (400 `price-invalid`). The overlap rule compares a text group column without regard to case in every stack (`EffectiveDatePlan.FoldsCase`), so lists written as `usd` and `USD` are one group; the Python overlap check also reads the caller's tenant. The shape is found through `TableShapes.PriceList` and `TableShapes.PriceListHead`, and the shape detector suggests the setting (`DatabaseShapeDetector`). Played with `Docs/Verification/Tools/price_check.py` and `price_race_check.py` over `Schemas/price_lists.sql` through `price_sqlite_run.py`, and for the owner and the tenant with `price_scoped_run.py`.

**`BankAccountTables=Table[:IbanColumn[:AccountColumn[:RoutingColumn]]]`, `InstallmentTables=Table:DocumentColumn:DocumentTable:TotalColumn[:SequenceColumn[:DueColumn[:AmountColumn]]]` and `PaymentTermsTables=Table:DocumentColumn:DocumentTable:DocumentDateColumn[:TermsColumn[:DueColumn[:TermsTable[:DaysColumn]]]]`** (ASP.NET with `AccessMode=Ef`, Python and Rust; `PaymentPlan`, `PaymentWriter`, `PythonPaymentWriter`, `RustPaymentWriter`): `CheckAccountAsync` writes the IBAN without spaces and in upper case and refuses one whose length does not fit its country or whose check digits fail (a country with no IBAN is refused), checks a routing number's check digit and an account number of 4 to 17 digits, and needs an IBAN or an account number with a routing number (400 `/problems/payment-invalid`). `CheckInstallmentAsync` refuses a document that does not exist, a sequence number or an amount that is not above zero, a sequence number another installment of the document has, a due day that does not follow the numbers (an earlier number may not fall due later) and amounts that add up to more than the document's total (400 `/problems/installment-over-total`); the amounts are added in memory, as decimals, so a SQLite database answers as the others do. `GET schedule?document=` answers `total`, `scheduled`, `remaining`, `complete` and `installments`. `CheckDueAsync` gives a row with payment terms and no due day the date of the document plus the days to pay and refuses a due day before the date of the document. A table with a column that looks like a card number, a security code or an expiry is refused at generation (a card is never stored). The words are `PaymentWords`; `Problems.cs` gets `PaymentInvalid` and `InstallmentOverTotal` (regenerate the essentials of an existing project with `--replace`). `PaymentTermsTables` also takes the discount, the penalty and the total columns (`EarlyDiscountPercent`, `EarlyDiscountDays`, `LatePenaltyPercent`, `Total` by default, used only when the tables have them): `GET payable?id=&on=` answers `total`, `discount`, `penalty`, `payable`, `day`, `dueDate` and `rule`; the discount applies up to and including the last discount day counted from the date of the document, and the penalty (a flat percent of the total) from the day after the due day; the amounts are rounded to the scale of the total column. A date column is a `DateTime` in the generated entities, so the date of the document and the due day are compared as days.

**`LedgerTables=Table:DocumentColumn:DocumentTable:TotalColumn[:KindColumn[:StatusColumn[:AmountColumn[:GatewayIdColumn[:IdempotencyKeyColumn]]]]]`** (ASP.NET with `AccessMode=Ef`, Python and Rust; `LedgerPlan`, `LedgerWriter`, `PythonPaymentWriter`, `RustPaymentWriter`): an append-only payment ledger. The table is also a log table (`LogTablePlan.Entries` includes it), so the read-only list and the 405 on POST, PUT and DELETE come from the log mechanism and this template adds two routes to the table's `<Table>Shape` class: `POST <route>/record` (`RecordAsync`, which stamps the log timestamp when the row has none, runs `CheckLedgerAsync`, adds the row and answers 201) and `GET <route>/paid?document=` (`PaidAsync`). `CheckLedgerAsync` writes the kind and status in lower case, refuses an unknown kind or status, a missing document, a refund that is not negative, any other kind that is not positive, a blank gateway id or idempotency key (all 400 `payment-invalid`), a gateway id or idempotency key already recorded (409 `ledger-duplicate`) and a succeeded refund above the captured amount less the refunds so far (400 `refund-over-paid`). The amounts are added in memory as decimals. Since there is no save check on a log table, nothing else calls `CheckLedgerAsync`.

**`TaxLines=InvoiceLine:TaxCategoryId:TaxRate:LineTotal:TaxAmount:TaxCategory:Rate[:ValidFrom[:ValidTo[:LineDate[:InvoiceId[:Code[:GroupColumns]]]]]]`** (ASP.NET with `AccessMode=Ef`, Python and Rust; `TaxLinePlan`): a document line that carries the tax rate of its category. `CheckTaxAsync` runs in the table's `CheckSaveAsync`, so the REST and OData routes both use it (`apply_tax` in the Python router, `apply_tax` in the Rust one, called before the row is written; an update there ignores the body's rate and tax amount). A category column that allows NULL gives a line with rate 0 and tax 0. The rate is a fraction (0.08 for 8 percent, as the category's `Rate` holds it), never money: it is not shown with a currency symbol (`TaxLinePlan.RateColumns` adds the line's and the category's rate column to `NotMoneyColumns`), the subtotals say it as a percentage, and the tax is the taxable amount times it. The OData routes run the rule too (played by hand over SQLite with `OData=true`: a POST under `/odata` copies the rate and writes the tax, an expired or unknown category is the same 400, a PUT recomputes the tax and keeps the rate). Played with `tax_check.py --dated` over `Schemas/tax_lines.sql` (`tax_sqlite_run.py` runs it on the three APIs over SQLite; Rust there has `f64` columns, so the `Decimal` variant is not played).

**`AllowanceCharges=InvoiceAllowanceCharge:IsCharge:BaseAmount:Percentage:Amount[:InvoiceId[:InvoiceLineId]]`** (ASP.NET with `AccessMode=Ef`, Python and Rust; `AllowanceChargePlan`, `AllowanceChargeWriter`, `PythonAllowanceWriter`, `RustAllowanceWriter`): a table of allowances (discounts) and charges (surcharges). The four columns default to `IsCharge` (a yes/no column that cannot be NULL, true is a charge), `BaseAmount`, `Percentage` (10 is 10 percent) and `Amount` (the base and the percentage are decimal, double or float and may be NULL, the amount cannot be NULL). `CheckAllowanceCharge` runs before every create and update: a negative value is refused, a percentage needs a base amount, a percentage and a base write the amount (base times percentage over 100, rounded half away from zero to the amount column's scale; an amount sent with them is ignored), a base and an amount with no percentage write the percentage, an amount alone is kept, and a row with none of these is refused (400 `allowance-charge-invalid`). The amount is stored positive: the flag says whether it is added (a charge) or taken off (an allowance). With the `InvoiceId` part (the column that points at the document or line the row sits on), `GET <rows>/allowance-charge-totals?document=` answers `allowances`, `charges`, `net` (charges minus allowances) and `rows`. With the `InvoiceLineId` part too (a whole-number column that is not the document column; the entry needs the document column), a row sits on a document and, when the column is given, on one of its lines, and `&line=` narrows the totals to the rows of that line. A table with its own owner column (`OwnedTables`) or its own tenant column counts only the rows the caller may see in the totals (ASP.NET through `IOwnerScope` and the tenant filter, Python through `only_owned` and the tenant filter, Rust through the scoped read); the tenant table itself and a table that is owned through its parent are refused. The shape detector suggests a table whose name says allowance, charge or discount and that has the yes/no, base, percentage and amount columns. The reason is a plain text column, or a foreign key to a look-up table, which gets the drop-down like any other key. Python (`check_allowance`, `allowance_charge_totals`) and Rust (`check_allowance`, `allowance_charge_totals`; computed in `Decimal` when a column is one, otherwise in `f64`, since SQLite has no `rust_decimal`) answer the same. Screens: with the `InvoiceId` part the list of the table in React, Angular, Blazor, Uno and WinUI3 has a document box and a `Show totals` button that says `Allowances 55.02, charges 60, net 4.98 (5 rows)` (`AllowanceScreens`), and the WinUI3 dialog, which writes through its own context, runs the same rule before it saves. When the table is the child grid of a document's master-detail page and its document column is that key, the page or dialog (React, Angular, Blazor, Uno, WinUI3) shows the same line under the grid. The generated tests of all three APIs (`AllowanceApiTests`, `PythonAllowanceTests` with PY_TestAllowance, `RustAllowanceTests` with RS_TestAllowance) play the amount, the percentage, the three refusals, the totals and, with a line column, the totals of one line; the Python and Rust ones need a table without a foreign key that is not the key (`AllowanceTestPlan`). The total of a document built from its lines (the header totals) is a separate entry that has not been built. Played with `allowance_check.py` over `Schemas/allowance_charges.sql` (`allowance_sqlite_run.py --stack api,python,rust`, SQLite), over SQL Server (ASP.NET; `live_party_run.py mssql ... --allowance`, the table `InvoiceAllowanceCharge` of `InvoiceSystemTableShapes.sql`) and over PostgreSQL and MySQL (ASP.NET, Python and Rust; `Schemas/allowance_charges_postgres.sql` and `allowance_charges_mysql.sql`); `Matrix/allowance_screens.settings`, `allowance_react.settings` and `allowance_angular.settings` build and test every stack's screens, and `Schemas/allowance_charges_document.sql` with `Matrix/allowance_document*.settings` the line under an Invoice's grid; with the check switched off in the generated file the checks fail.

**`DocumentTotals=Invoice:InvoiceLine:InvoiceId:LineTotal:Lines=ItemsTotal:Allowances=AllowanceTotal:Charges=ChargeTotal:TaxExclusive=TaxExclusive:Tax=TaxTotal:TaxInclusive=TaxInclusive:Prepaid=Prepaid:Rounding=Rounding:Payable=Payable[:Currency=Currency][:Round=CHF/0.05][:Decimals=JPY/0]`** (ASP.NET with `AccessMode=Ef`, Python and Rust; `DocumentTotalsPlan`, `DocumentTotalsWriter`, `PythonTotalsWriter`, `RustTotalsWriter`): a document header whose totals the server writes from the rows of the document. After every save that touches the header, a line, or an allowance or charge row of the document (`AllowanceCharges`) the totals are worked out again from the rows in the same transaction: the lines total is the sum of the line amounts, the allowances and the charges are the sums of the allowance table's rows, tax-exclusive is lines minus allowances plus charges, tax is the sum of the lines' tax amounts (`TaxLines`), tax-inclusive adds the two, and payable is tax-inclusive minus the prepaid amount plus the rounding. The prepaid amount is the one column a client writes; the rounding brings the payable amount to a multiple of the currency's increment (`Round=CHF/0.05`, or `Round=*/0.05` for every currency). Every amount is rounded half away from zero to the scale of its column, or to the decimal places of the currency (`Decimals=JPY/0`, or `Decimals=*/3`; at most the column's scale, so a yen invoice is whole yen in every total), and the next one is worked out from the rounded ones. A value a client writes into a total is replaced, not refused (a form that opened before a line changed would otherwise be refused on save); the forms show the totals as text. A move of a line to another header brings both headers up to date. ASP.NET: the generated context (`CS_DbContext`, which the desktop apps use too) wraps `SaveChanges` in a transaction, notes the headers the save touches (the old header of a changed line is read from the database, since an update that came in as a whole row has no old value), and after the save writes the totals with `ExecuteUpdate`; Python: session events `before_flush` and `after_flush`; Rust: the header, line and allowance routes save inside a transaction (`insert_in`, `update_in`, `delete_in` of the repository). The header row is updated before the first write of a save, in key order, because a line's foreign key check holds a shared lock on its header and two saves of one document would otherwise deadlock (SQL Server and InnoDB). `GET <header route>/document-totals-check?id=` lists the headers (one, or up to a thousand) whose stored totals differ from their rows. A line table in `SoftDeleteTables` is refused, since its deletes do not pass through a save. Played with `Docs/Verification/Tools/document_totals_check.py` and `document_totals_race_check.py` over `Schemas/document_totals.sql` (`document_totals_sqlite_run.py`) and over SQL Server, PostgreSQL and MySQL (`live_totals_run.py --kind mssql|pg|mysql`). A header or line table limited to an owner or a tenant is served by all three APIs (the Python and Rust check route lists only the caller's headers); only the tenant table itself is refused when Python or Rust is in `Stacks`. `AllowanceTax=TaxAmount` (the tax amount column of the allowance table, which is listed in `TaxLines` itself, for example `InvoiceAllowanceCharge:TaxCategoryId:TaxRate:Amount:TaxAmount:TaxCategory:Rate:ValidFrom:ValidTo`) adds the tax of each allowance row to the tax total, minus for an allowance and plus for a charge. The allowance row is a tax line like any other: it copies the rate of its category when it is created or its category changes, keeps it after a later rate change (so the check route and the totals do not move), and is refused with 400 when the category is unknown or not in force on the day. The save check of the tax runs after the allowance amount is worked out. The rate and the tax amount are text on the form, as on a line. A line table or an allowance table scoped to an owner or a tenant works in all three APIs (an allowance table scoped only through its document's owner too; the allowance totals route and the Python and Rust tax-subtotals and check routes show only the rows the caller may see). Clicked through in React, Angular, Blazor, WinUI3 and Uno (`DocumentTotals` over `Schemas/document_totals.sql`; `winui3_allowance_tax_check.ps1` for the two desktop apps): the allowance dialog has a Tax Category drop-down and no rate or tax input, the Edit dialog shows the rate and the tax amount as text, the grids show the rate as a percentage (the React and Angular invoice dialog's child grids too, `ChildGrid.RateColumns`), a taxed allowance and charge change the invoice's totals, and an expired category is refused with no row written (not seen in Uno, whose drop-down UI Automation cannot pick from). The owner and tenant cases are played over SQLite, PostgreSQL, MySQL and SQL Server (`live_totals_scoped_run.py`). The generated tests of the Python and Rust APIs (`PY_TestTotals` and `RS_TestTotals`, from `DocumentTotalsTestPlan`; the prepaid case only without a `Round=` rule) play the totals a client writes replaced, the lines total after a line is added or removed, the payable amount after the prepaid amount changes and the check route. The shape detector suggests the setting for a header whose columns are named like the totals (`DatabaseShapeDetector.DocumentTotals`).

Shared code in Core: the C# that gives a tax line its rate and tax (`TaxRateBlock`) and works out an allowance or charge row (`AllowanceChargeBlock`) is written once and used by the API's check (`TaxLineWriter`, `AllowanceChargeWriter`) and by the WinUI3 dialog's check (`TaxScreens`, `AllowanceScreens`); each caller passes its variable names and how it refuses a row. `DocumentTotalsCurrencyRules.Split` gives the C#, Python and Rust totals writers the rules of one currency and the rule of every other currency, `ColumnModel.IsFractionalColumn` is the one test for a decimal, double or float column, and `TableModel.FindColumn` the one column lookup of the plan classes.

The generated ASP.NET tests (`RateApiTests`, appended to the table's test class by `RowShapeTests`) play the rate table (the rule, the invalid cases, the lookup, and the inverse with `RateInverse`) and the document (written with the rate in force, kept when only the amount changes, a new date takes that date's rate, the base currency has rate 1, no rate is refused). The generic tests write the base currency into a document's currency column and never change it, since a save looks the rate up (the Rust `test_bodies.rs` does the same). `PY_TestRates` also writes `tests/test_rate_documents.py` and `RS_TestRates` `tests/api/rate_document_routes.rs` (`PythonRateDocumentTests`, `RustRateDocumentTests`, planned by `RateDocumentTestPlan`): the document written with the rate in force and its currency trimmed, a new date takes that date's rate (when the table has a date column), an update ignores a rate and converted amount sent by the caller, the base currency has rate 1, and a currency with no rate is a 400 `rate-needed`. The plan needs identity keys in both tables, currencies of three characters or more, and no other required column of either table that is a foreign key or in a unique index. With `RateInverse` the rate tests of both stacks also play a newer opposite rate answered as one divided by it (the Rust test does not check the header, whose reply type holds no headers). Played with `Docs/Verification/Tools/rate_document_check.py` over `Schemas/rate_documents.sql`, and over SQL Server, PostgreSQL and MySQL with `live_rate_run.py --documents`.
