# API_RowShapes_v1 and the TreeTables, ContentTables, AssetTables, SoftDeleteTables and EffectiveDatedTables settings

Three table shapes that an ordinary list-and-edit API gets wrong: a table that refers to itself (a tree), a table whose rows are flagged instead of removed (soft delete), and a table whose rows are valid for a period (effective dating). The rules are `TreePlan`, `SoftDeletePlan` and `EffectiveDatePlan` in Core (`RowShapePlans.cs`); `RowShapeWriter` writes the C#. The tree, soft delete and effective dating are also written for the Python and Rust APIs (see below), and so are the content tables. All three need the ASP.NET API and `AccessMode=Ef`, a single whole-number key, and they are off until the project lists the table. A table can have more than one shape (a category tree with soft delete); the user table cannot have any.

`API_RowShapes` writes `Apis/RowShapes.cs`: per table a static `<Table>Shape` class and `RowShapeApi.Register`, called by `API_Registration`. The table's own API (`API_Crud`) overrides `BeforeSaveAsync` and `BeforeDeleteAsync` to call `CheckSaveAsync` and `CheckDeleteAsync`. Those hooks used to exist only with `ApiAuth`; the `CrudApi` essentials now write them also for a project that lists a shape, so **refresh the CrudApi essentials** (the essentials replace option) in an existing project. With `ApiAuth` the extra routes need a signed-in caller, and `deleted` and `restore` need the administrator role.

## TreeTables=Category:ParentCategoryId:3

A table, optionally its parent column (default: the table's one foreign key to its own key) and optionally the deepest level allowed (a root is level 1; blank: no limit). The parent column must allow NULL.

| What | How |
|---|---|
| A parent that is the row itself, or one of its own descendants | 400, `/problems/tree-cycle`. The check walks up from the new parent, so it also stops a cycle that is already stored. |
| A level past the limit | 400, `/problems/tree-too-deep`. The row's level plus the height of the subtree under it, so moving a branch cannot push its leaves past the limit. |
| Delete of a row with children | 409, `/problems/tree-has-children`. |
| `POST {id}/promote-children` | The children become children of the row's own parent (roots when it is a root); the row stays, so it can be deleted next. 404 for a missing row, otherwise `{ moved }`. |
| `GET tree` | Every row depth first, children after their parent and by name (the `Name` or `Title` column, else the key): `{ id, parentId, depth, hasChildren, text }`. Only a row with no parent is a root: a row whose parent is soft deleted is left out with the rest of its branch. |

## ContentTables=Post or Post:Title:Slug:Status:PublishedOn

Posts, pages and articles. A table, then the title (the text the slug is made from), the slug, the status and the published-on columns; each defaults to the column of that name (the title also to `Name` or `Headline`, the stamp also to `PublishedAt`). The slug and the status are text columns that cannot be NULL (the status needs room for `published`, the slug for 14 characters), the published-on column is a date and time that allows NULL and is optional. The rules are `ContentPlan` and `ContentWords` in Core; the text is `RowShapeWriter`.

| What | How |
|---|---|
| The slug | Made from the title when the slug is blank on create: lower case, accents dropped, letters and digits with single hyphens, cut to the column's length. A made slug that is taken gets `-2`, `-3`. A slug the caller sends is made into the same form and refused when taken: 409, `/problems/content-slug-taken`. |
| A new title | Does not move the slug: an update with a blank or an unchanged slug keeps the stored one. A different slug is a rename on purpose and is checked like a new one. |
| The status | Owned by the routes: a new row is `draft` whatever it says, and a save puts back the stored status and published time. |
| `POST {id}/publish` | Status `published`; the published time is stamped the first time and kept after that. Answers the row; 404 for a missing row; doing it again changes nothing. |
| `POST {id}/unpublish` | Back to `draft`. |
| `POST {id}/archive` | Status `archived`. |
| `GET public` | The published rows, the newest published first, `?pageNumber=&pageSize=` (20 by default, at most 100). No sign-in (`AllowAnonymous` with `ApiAuth`). |
| `GET public/{slug}` | One published row; a draft or an archived row is 404. No sign-in. |

The public routes answer every column of the table unless `ContentPublicColumns=Post:Title+Slug+Body+PublishedOn` names the columns to answer (a row of anonymous objects, so a private column such as an author's note never leaves the server; the slug is always in the answer). The slug is unique among the rows the context can see; give the column a unique index too: without one two requests at once can still store the same slug, and the generator says so in its warnings. With the index the second one is refused by the database. Not built yet: a publish that needs a second person, a body editor and full-text search.

**Python and Rust.** Both write the same rules into the table's own router (`PythonContentWriter`, `RustContentWriter`; the words are `ContentWords` and `ContentApiWords`): the same routes, problem type and sentences as the table above. With `ApiAuth` the two public reads are left out of the sign-in check: Python lists the table's `public_router` in `routes.public_routers` (`PY_Mod`; `main.py` includes it first), Rust merges `routes::public_router()` after the sign-in layer (`RS_Mod`, `main.rs`). The Rust crate gets `unicode-normalization` for the accents. A tenant-owned content table and a table also in `RowApprovals` stop the run with a sentence for these two APIs. `Docs/Verification/Tools/content_check.py` plays the rules against a running API.

**A tenant-owned content table** (`TenantTable` with the tenant column on the table) needs `TenantHostColumn`: the anonymous public routes have no signed-in tenant, so they answer the rows of the tenant the request host names (`acme.example.com` is the tenant whose host column is `acme`; `TenantHost.FindAsync`, the rule that already refuses a token on another tenant's host). A host that names no tenant (`localhost`, an address) answers an empty list and a 404, never another tenant's rows. The public query ignores the context's filters and asks for that tenant itself, and for `!IsDeleted` when the table is also in `SoftDeleteTables`. Without `TenantHostColumn` the generator stops with a sentence that says to set it or to list the table in `NoTenantTables`. Everything with a caller stays in the caller's tenant through the context's filter: the save rules, publish, unpublish and archive (another tenant's row is a 404), and the slug check, so a slug is unique per tenant and two tenants may both have `welcome`. Give the table a unique index on the tenant column and the slug. The browser must reach the API on the tenant's host name (the public pages of a front end served from another host name read the tenant of that host). The generated tests of the table do not read the public routes (the test tenant has no host name); `TenantBypassApiTests` plays two tenants with host names: the same slug in both, a rival's publish is a 404, each host answers its own row, a host that names no tenant answers none. `Docs/Verification/Tools/Matrix/tenant_content.settings` is the matrix.

**Publishing that needs a second person.** A table that is in `ContentTables` and also in `RowApprovals` (see `API_Approvals_v1.md`) is not published by `POST {id}/publish`: the route asks for approval, the same request as `POST {id}/request`, and answers the row with the state `pending`. The approval publishes the row (the first time with its published time), a rejection or a withdrawal makes it a draft again, and the requester cannot approve their own request (403, the four eyes of the approvals). A pending row is not public. A refusal of the request is the answer: 403 `approval-requester-unknown` for a person who is not a row of the user table, 409 `approval-wrong-state` while a request already waits, and the project's own `ApprovalHooks.Validate`. Unpublish and archive need no approval, and end a request that still waits for the row (it is withdrawn), so a late approval changes nothing. A request made on the approvals page or from the row's Approval panel works the same way. The state is kept in the table's own status column (`pending` fits any column that holds `published`); `MarkPendingAsync`, `PublishPendingAsync` and `RevertPendingAsync` of the table's `Shape` class (the WinUI3 app: `<Table>Content`, written from the same `ContentRulesWriter` text) are what the approval routes call, in the decision's transaction. The screens show the state in the Status column and offer no Publish on a pending row. The WinUI3 app, which reads the database itself, asks through its in-process `ApprovalService`; the Uno app calls the API. `API_TestContentApprovals` writes `<Table>ApprovalPublishApiTests.cs` (the request, the four eyes, the approval, a rejection, an archive that ends the request, a stranger) over the people and the row that `ApprovalTestSeed` puts in the scratch database; the WinUI3 `ApprovalServiceTests` have the same cases in process. Not covered: the Python and Rust APIs (no content tables there yet).

**Screens.** The list page of every front end (React, Angular, Blazor, Uno, WinUI3) shows Publish, Unpublish and Archive on a row, each only when it would change something (Publish for a draft or an archived row, Unpublish for a published one, Archive for any row that is not archived). In the form the status and the published time are text, not boxes, and the slug box is not required and says it is made from the title when left blank (a placeholder on the web). `ContentScreens` in Core holds the captions, the failure sentences and the tests of a row's state; `FormColumn` makes the status and the published time system-stamp fields and the slug not required, so every stack's required check follows. The web pages and the Uno app call the API (`publish`, `unpublish` and `archive` on the client). The WinUI3 app reads the database itself, so it makes the same guarded UPDATE (`ContentScreens.SetCalls`) and runs the same slug and status rules before a save: `WinUI3_Content` writes `Repositories/Content.cs` with a `<Table>Content` class whose `MakeSlug` and `PrepareAsync` are the text the API writes too (`ContentRulesWriter`). The OData pages and the pages of a table with children have them too: an OData page publishes through the REST client and always asks for the status, even when the person hides its column. The edit dialog of a saved row has the same buttons (a new row has none): a click changes the state on the server and the dialog shows the new status and published time while the other fields keep what was typed, so a save afterwards still writes the typed values. The desktop dialogs show the slug box with the hint "Leave blank to make it from the title" as well.

## AssetTables=Asset or Asset:StorageKey:FileName:MimeType:Size:Url

A table whose rows point at a stored file: the row holds the key in the store, the name the file had, its type and its size, never the bytes. A table, then the columns of the storage key, the file name, the file type, the size in bytes and the optional download address; each defaults to the column of that name (`StorageKey`, `FileName`, `MimeType`, `SizeBytes`). The key column cannot be NULL and needs room for 44 characters, the name column cannot be NULL, the size is a whole number, and every other column must allow NULL or have a default, because the upload route fills only these. The rules are `AssetPlan` and `AssetWords` in Core; the text is `RowShapeWriter`. A table also in `SoftDeleteTables`, `OwnedTables` or the tenant table stops the run with a sentence.

| What | How |
|---|---|
| `POST upload` | A multipart form with a field named `file` (the first file when none has that name). The file is written to the store under a key the server makes (32 hex digits and the lower case extension), then the row is added; if the row cannot be saved the file is removed again. Answers 201 and the row, with the download address in the `Url` column when there is one. |
| No file in the form, or an empty one | 400, `/problems/asset-no-file`. |
| A file over `AssetMaxBytes` (default 10485760) | 413, `/problems/asset-too-large`. |
| A type not in `AssetAllowedTypes` (`image/*,application/pdf`; empty for any) | 415, `/problems/asset-type-not-allowed`. The type is the one the client sent, lower case and without parameters. |
| `GET {id}/download` | The file with the row's type and name as a download (`Content-Disposition: attachment`, `nosniff`), range requests allowed. 404 for a missing row, 404 `/problems/asset-file-missing` when the store has no file for the row. Needs a sign-in with `ApiAuth`. |
| A delete | The row is deleted and then the file is removed from the store (`AfterDeleteAsync`, a new hook of the CRUD base: refresh the `CrudApi` essentials in an existing project). A delete the database refuses (a row that others refer to) keeps the file. A key with no file behind it is not an error. |
| The ordinary create and update routes | The storage key cannot be named by a request. A row made by the ordinary create holds an unattached key (`unattached-` and a guid) and has no file; an update keeps the stored key, type and size and may change the name and the other columns. |

The store is `IAssetStore` (`SaveAsync`, `OpenAsync`, `DeleteAsync`). The default `LocalFolderAssetStore` keeps one file per key in `AssetStoreFolder` (default `App_Data/assets`, relative to the folder the API runs in) and refuses a key that could leave the folder. To keep files in S3 or Azure Blob, register your own `IAssetStore` as a singleton; `RowShapeApi.Register` hands the routes the application's services. Several asset tables share the store and the limits.

**The insert.** The upload writes the four columns it knows (key, name, type, size) with one INSERT and reads the new key back (`OUTPUT INSERTED` on SQL Server, `RETURNING` on PostgreSQL and SQLite, `LAST_INSERT_ID()` on MySQL), so the database fills every other column with its default; an entity would send the CLR default of each (a `datetime` column got 0001-01-01 and SQL Server refused it).

**Python and Rust.** Both write the same routes, sentences and problem types (`PythonAssetWriter`, `RustAssetWriter`; the words are `AssetWords`) into one file for the database, `app/routes/asset_files.py` and `src/routes/asset_files.rs` (`PY_Assets`, `RS_Assets`), and `PY_Mod` and `RS_Mod` list it before the tables' routers. The store is `AssetStore` (`LocalFolderAssetStore`; `ASSET_STORE_FOLDER` or `AssetStoreFolder`): Python's `use_store()` swaps it, Rust's `use_store()` must be called before the first request. Python keeps the storage key out of a request's hands with SQLAlchemy events on the table's class (an ordinary insert gets an unattached key, an update restores the stored key, type and size, a delete removes the file once it commits); Rust has no events, so `RS_Routes` adds the same three steps to the table's own create, update and delete. `requirements.txt` gets `python-multipart` and `Cargo.toml` gets axum's `multipart` feature. The tests are `tests/test_assets.py` (`PythonTests=true`, `PY_TestAssets`) and `tests/api/asset_routes.rs` (`RustTests=true`, `RS_TestAssets`); both put the files in a temporary folder.

**Screens.** The list page of every front end (React, Angular, Blazor, Uno, WinUI3, and the OData pages that are the same templates) has an Upload control in its bar and a Download button on a row; no binary column is ever shown. `AssetScreens` in Core holds the captions, the failure sentences (`Problem while uploading!`, `Problem while downloading!`) and the `accept` list of the file box (`AssetAllowedTypes`). In the form the storage key, the file type and the download address are text, not boxes, because the upload owns them (`FormColumn` makes them system-stamp fields); the size stays a number box that the server ignores.

| Front end | Upload | Download | The client behind it |
|---|---|---|---|
| React | a hidden file input behind an Upload button | `Download` saves the blob | `uploadFile` and `downloadFile` in `api/client.ts` (essentials: refresh them in an existing project), `upload` and `download` in the table's api module |
| Angular | the same, with a template reference | the same | `upload` and `download` of the table's service (`FormData`, a blob answer, the name from `Content-Disposition`) |
| Blazor | an `InputFile` in a label (the file is read up to `AssetMaxBytes`) | `DownloadAsync` hands the bytes to `codegenSaveFile`, a script `wwwroot/index.html` defines (essentials: refresh it) | `UploadAsync(Stream, name, type)` and `DownloadAsync(id)` of the table's client (`ApiClientCode`, shared with Uno) |
| Uno | a `FileOpenPicker` (attached to the window on the Windows head through `App.MainWindow`, a new member of `App.xaml.cs`: refresh the essentials) | a `FileSavePicker` and `FileIO.WriteBytesAsync` | the same client |
| WinUI3 | a `FileOpenPicker`; the app reads the database itself, so `Assets.cs` (`WinUI3_Assets`) holds the store and `<Table>Assets.UploadAsync` copies the file into the store and adds the row | a `FileSavePicker`; `ExportAsync` copies the stored file there | none: the dialogs call `<Table>Assets.PrepareAsync` before a save, and a delete reads the key first (`RememberFileAsync`) and removes the file after (`AfterDeleteAsync`) |

**The edit dialog** has the same two buttons and a picture. A new row's dialog has an Upload button: the file makes the row (the storage key, name, type and size come from the server). React, Angular and Blazor go on editing the saved row, so a caption can be typed and saved; WinUI3 and Uno close the dialog and the list shows the new row. A saved row's dialog has a Download button, and, when the stored type is an image other than SVG, a picture at most `AssetScreens.PictureEdge` pixels wide: React and Angular read the bytes through the client (an image tag cannot send the sign-in token), Blazor puts them in a `data:` address, the desktop apps decode them into a `BitmapImage`. `AssetDialogCode` in Core writes the desktop dialogs' XAML, handlers and view-model members for WinUI3 (through `<Table>Assets.CopyFileAsync`, which reads the store and never the database) and Uno (through the API client). A browser app on another origin reads the downloaded file's name from `Content-Disposition`, so the API's CORS policy (ASP.NET, Python and Rust) exposes that header when the project has an asset table.

Not covered: a table limited to an owner or a tenant; a `varbinary` column; a store other than a local folder (S3 and Azure Blob are the owner's `IAssetStore`). `Docs/Verification/Tools/Schemas/assets.sql` (and `assets_postgres.sql`, `assets_mysql.sql`) is the scratch schema: `python new_scratch_project.py Ast --schema assets --stack api,python,rust --set AssetTables=Asset:StorageKey:FileName:MimeType:SizeBytes:PublicUrl,Document --set ApiTests=true --set PythonTests=true --set RustTests=true`.

## PolymorphicLinks=Attachment:OwnerType:OwnerId:Product|Opportunity|Customer

A link table whose far side is a pair, a record type name and a record id: a brochure attached to a product or an opportunity, a comment or a note on any record. A foreign key cannot hold that, so the checks are code. The table, the type column, the id column and the tables the type may name (at least two, each with a single whole-number key) are the setting; `:remove` after them removes a deleted row's links instead of refusing the delete. The id column has no foreign key; the table may also be an asset table (the brochure is a file).

| Where | Rule |
|---|---|
| Create and update of the link table | The type is trimmed and matched to a listed table without regard to case; no match is a 400 `link-type-unknown` that names the listed tables. The type is written as the table's own name (`product` is saved as `Product`). The id must be a row of that table, else a 400 `link-target-missing`. |
| Delete of a listed table's row | Refused with a 409 `link-target-in-use` while a link table without `:remove` has a row naming it. With `:remove` the links go after the row is gone (`AfterDeleteAsync`). |
| The type column | `PolymorphicPlan.ApplyChoices` gives it the listed names as its choices, so every front end shows a drop-down, the validators name the values and the generated tests take the first. A column that already lists values (a CHECK list) keeps its own. |
| The attachments grid | `PolymorphicPlan` adds a child to each listed table (a `ChildForeignKeyModel` with a `TypeColumn` and a `TypeValue`, kept out of the foreign keys the database declares), so the listed table's screen is a master-detail screen and its edit dialog shows the link table's rows whose id is the row and whose type is the table (React, Angular, Blazor, WinUI3 and Uno read it as any child grid; the web screens filter the whole list, the desktop ones filter in the query). A link table with no screen of its own (too small to get one, or left out of `Screens`) gives no grid. A delete the link table refuses answers 409, which the React pages show as "in use". |

`RowShapeWriter` writes `CheckLinkAsync`, `CheckLinksAsync` and `AfterDeleteAsync` in the table's `<Table>Shape`; Python (`PY_Links`, events on the model classes, `app/routes/link_rules.py`) and Rust (`RS_Links`, `check_*`, `refuse_linked_*` and `remove_links_*` called from the routes, `src/routes/link_rules.rs`) have the same rules and sentences. `Tools/polymorphic_check.py` plays them over HTTP against any of the three over `Tools/Schemas/polymorphic.sql`. The generated generic add, change and remove tests are not written for a link table (a row of it must name a row of another table). Not covered: an "attachments" section on the screen of each listed table, a link table or listed table that is limited to an owner or a tenant, and a listed table with a text key.

## SoftDeleteTables=Customer,Order:IsRemoved

A table and optionally the yes/no column (default `IsDeleted`, NOT NULL). `DeletedOn` (date and time) and `DeletedBy` (text), both allowing NULL, are filled when the table has them; `DeletedBy` is the signed-in name with `ApiAuth`.

- `DELETE` sets the flag instead of removing the row and answers 200; the delete of a row that is already flagged is 404.
- `CS_DbContext` adds `HasQueryFilter(e => !e.IsDeleted)`, so a flagged row is in no list, search, look-up or read of the generated API, and a PUT to it is 404. Regenerate the context. The Python and Rust APIs have their own filter (see below); a WinUI3 or Uno app over the context of its own and reports do not know it.
- `GET deleted` lists up to 500 deleted rows, the last deleted first (an administrator).
- `POST {id}/restore` clears the flag and the stamps and answers the row; 404 when there is no such row, 409 `/problems/not-deleted` when it is not deleted (an administrator).

A row that other rows refer to is not removed by a soft delete, so the foreign keys keep pointing at it; a unique index still counts it.

## DefaultRowTables=CustomerAddress:IsDefault:CustomerId+AddressType

A table of which exactly one row per group is the default (an address of a customer per type). The yes/no column cannot be NULL and the group is made of one or more other columns (`+` between them); the key is a single whole number.

| Rule | How |
|---|---|
| A save with the mark | `CheckDefaultAsync` clears the mark of the others of the group in a transaction that the save of the row commits (`DefaultRows.InSaveTransactionAsync`, committed on `SavedChanges`, rolled back on `SaveChangesFailed` or when the request ends without a save), so a unique index on the group where the flag is set is never broken |
| A save without the mark | a row that is alone in its group, or that was the only default, is marked instead: a group that has rows has a default |
| `POST {id}/make-default` | moves the mark in one transaction; a row that is the default answers 200 and changes nothing; a missing row is 404 |
| A delete of the default row | `CheckDefaultDeleteAsync` hands the mark to the next row of the group (the lowest key) in one transaction before the delete runs |
| Clone | none: a copy of the default row would be a second default (`CloneShape`) |
| The screens | a "Make default" button on every list row that is not the default of its group (`DefaultRowScreens`): React, Angular and Blazor call the route (`makeDefault`, `MakeDefaultAsync`) and read the list again, Uno calls it through its client, WinUI3 moves the mark in one transaction of its own context. The edit dialog of a saved row has the same button, and the flag is text there (`DefaultRowScreens.IsFlagColumn` makes it a system-stamp field): a new row is not given a mark by the form, the API gives the first row of a group the mark, and the WinUI3 dialog, which writes through its own context, does the same before it saves |

`RowShapeTests` writes two tests (a mark taken, `make-default`). Not served for a table limited to an owner or a tenant. Python (`PythonDefaultWriter`: `settle_default` and `promote_default` called before the commit, so the marks move in the transaction of the save; the helper runs inside `no_autoflush` so the row's own flag is not written before the old mark is cleared) and Rust (`RustDefaultWriter`: `settle_default` before the write; a row that asks for the mark while another row holds it is written without it and `move_default` moves it in one transaction right after) write the same rule and the same route; Rust moves the mark after the write, not in the same transaction, so a failure between the two leaves the old default in place.


## EffectiveDatedTables=Price:ValidFrom:ValidTo:ItemId+CurrencyId

A table, the first and the last day columns (the same date type; the first cannot be NULL, an empty last day is open) and optionally the columns that say what the row is a price of (default: every single-column foreign key). Both ends are inclusive.

- A save whose last day is before its first day: 400, `/problems/effective-range`.
- A save whose period overlaps another row with the same values in the group columns: 409, `/problems/effective-overlap`. A row is never compared with itself, so a change that keeps its own period is fine; a table with no group column is one group.
- `GET current?on=2026-10-27&itemId=5` answers the rows in effect on the day (today when `on` is left out), narrowed by the group columns that are given.
- The table gets no Clone: a copy would have the period of the row it copies.

## Generated tests, the http file and the clients

`API_Test` adds, to the table's own test class, the tests of each shape it has: cycles, delete with children and promote, the tree order and the depth limit; delete, hidden, listed as deleted, restore, restore twice and restore of a missing row; a backwards period, an overlap and a neighbouring period, the rows in effect on the first and last day and the days around them, and an open period. Every test makes its own rows with the sample body and removes them. The ordinary tests of an effective-dated table send periods of one day in the 19th century (before real data, after SQL Server's 1753) with a last day of their own, so they never overlap each other or a period that is open. The test that needs a group with no open period skips when the group has one.

`API_Http` writes the requests of the extra routes. The React, Angular, Blazor and Uno clients get `getTree`, `promoteChildren`, `getDeleted`, `restore` and `getCurrent` (`GetTreeAsync` and so on) for the tables that have the shape.

## Not covered

Screens: every front end has a "Show deleted" switch with Restore and a "Valid on" day for a table in `SoftDeleteTables` or `EffectiveDatedTables` (an OData page and a name and active table have them too; a log table and a single-row table cannot be listed in `SoftDeleteTables` or `EffectiveDatedTables`, and the generator says so: a log is only appended to and a single-row table keeps its one row). An OData page reads the deleted rows, Restore and the rows valid on a day from the table's REST client (React `<table>Api`, Angular `<Table>Service`, Blazor `ShapeClient`; Uno has both clients already). React, Angular and Blazor open a dialog (`RowShapeDialog`, one component each, written by the support or crud essentials) over the page, with the grid's columns, a Restore button per deleted row (an administrator; the 403 is told in words) and, for the valid-on dialog, a date box that asks `GET current?on=` again; closing it after a restore reads the grid again. WinUI3 and Uno put a toggle and a date picker in the bar above the grid: the grid then lists the deleted rows (Restore in place of Edit, Clone and Delete) or the rows in effect on the day, up to 500 rows in one list. WinUI3 reads through the repository (`<Table>Repo` gets `DeleteAsync` as a flag, `GetDeletedAsync`, `RestoreAsync` and `GetCurrentAsync`), so its Delete flags the row too and stamps `DeletedOn` but not `DeletedBy`; Uno calls the API. No tree screen yet: a tree as an indented list with expand and collapse and "add a child" is not written in any front end; the clients only have the calls. Only the tree is written for the Python and Rust APIs (`PythonTreeWriter` and `RustTreeWriter`, inside the table's own router): the cycle and depth checks on create and update, the refusal to delete a row with children, `GET tree` and `POST {id}/promote-children`, with the same problem types and sentences; the Rust tree is left out for a table limited to an owner or a tenant, and the Python tree limits its rows to the caller's tenant. Soft delete is written for them too (`PythonSoftDeleteWriter`; in Rust `RustTable` adds the flag test to every read and update statement of the table, and the repository gets `soft_delete`, `restore`, `deleted` and `exists_any`): the delete flags the row and stamps `DeletedOn` and `DeletedBy` (the caller's name, with sign-in), a flagged row is in no list, search, look-up, read or tree, a second delete is a 404, `GET deleted` and `POST {id}/restore` (administrator only with sign-in; 409 `not-deleted` for a row that is not flagged) list and bring back rows. In Python one listener on the session adds the flag test to every select of the table (the counterpart of the query filter); the deleted list and the restore ask for `include_deleted`. For a table limited to an owner or a tenant the Rust API hides and flags rows but writes no deleted list and no restore, since those would have to be limited too, and the Python API leaves the tenant table itself alone. Effective dating is written for them as well (`PythonEffectiveWriter`, `RustEffectiveWriter`): the backwards-period and overlap checks on create and update (the Python update reads the saved row for the columns the body leaves out; a flagged row is not compared) and `GET current?on=&<group>=`, with the same problem types and sentences. The Rust version is left out for a table limited to an owner or a tenant, and the Python overlap check does not limit itself to the caller's tenant (a group column is normally tenant-owned itself). `Docs/Verification/Tools/effective_check.py` plays the rules against a running API. `Docs/Verification/Tools/tree_check.py` plays the tree rules against a running API. The check that a parent is not a descendant and the overlap check read and then write, so two requests at the same moment can both pass; a unique index or a serializable transaction closes that. Soft delete does not cascade: the children of a soft-deleted tree row stay, and the tree answer leaves them out with their branch (only a row with no parent is a root). A tree cannot have a composite key, and the depth limit is per table.

Checked with `Docs/Verification/Tools/Schemas/row_shapes.sql` (a category tree with soft delete, a soft-delete table and an effective-dated price table): the generated API tests over a SQLite copy, with and without `ApiAuth`, and over the same tables on SQL Server, PostgreSQL and MySQL.
