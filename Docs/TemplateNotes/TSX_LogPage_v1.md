# TSX_LogPage_v1 and the LogTables setting

`LogTables=ErrorLog,UserSession:StartedOn` names the insert-only tables the application only reads: an error log, a session list, a data-change ledger. A table and, after a colon, the column it is ordered by (without one the plan picks the date-and-time column whose name says when something happened: `LoggedOn`, `OccurredOn`, `CreatedOn`, ...). The rule is `LogTablePlan` in Core; every layer asks it, so they agree.

A table in `QueueTables` (a work queue, `API_Queue_v1.md`) and the `<Table>Archive` table of an `ArchiveTables` entry (`SP_ArchiveJob_v1.md`) are log tables too: the plan lists them without a `LogTables` line, ordered by their created or event stamp. A log table is never guessed from its shape. A table that looks like one (a date and time column, nothing that edits it, a log-like name or a level and a message) is only mentioned in the run notes: "list it in LogTables".

## What a log table gets

- **API (ASP.NET).** `API_Crud` writes the class with `ReadOnly => true`: `CrudApi` then registers no create, update, delete or clone route (a POST, PUT or DELETE answers 405), and `NewestFirst` is the timestamp. The search takes `from` and `to` (the first and the last day, both included) on the timestamp and lists newest first when no sort is chosen (`SearchPlan.Range`, `DefaultDescending`; `CS_SearchQuery` and `API_Search` write them, `CS_Repo` passes them to WinUI3). A date that is not a date is a 400. The CSV export takes the same two parameters, lists newest first and stops at the first 10000 rows; there is no import. The `.http` file has no write request, and `API_Test` writes a read-only class (`ApiLogTests`: no route changes a row, the range, a bad date, the sorts, the export).
- **`SP_LogIndex`** writes `Sql/LogIndexes.sql`: an index on the timestamp (descending where the database has it) unless the table already has an index that starts with it. Review it and run it yourself; the generator never applies it.
- **Python, Rust.** `PY_Routes` and `RS_Routes` write the reading routes only (a POST, PUT or DELETE answers 405, there is no clone; on a work queue the POST is the enqueue of `API_Queue_v1.md`). The search takes `from` and `to` on the timestamp (the first and the last day, both included; a date that is not a date is a 400) and lists newest first when no sort is chosen. `PY_Csv` and `RS_Csv` give the export the same range, newest first, stopping at the first 10000 rows, and write no import route. `RS_Test` writes a test file that checks the reads, the range and the 405 of every write, and `RS_TestCsv` leaves the table out. On SQLite the Python range compares through `datetime()`, since SQLite keeps a date and time as text and a value without a fraction sorts before the same value with one.
- **OData.** A table in `LogTables` that `ODataTables` serves has the two reads only (list and read by key), and a write answers 405. No OData screen is written for it: the screens of a log table read the REST search, which has the date range.
- **React.** `TSX_LogPage` writes the page (`pages/<Table>Page.tsx`, the name `TSX_Page` would give it, so the menu needs no change) and its test; `TSX_Page` writes nothing for the table. It opens on a filter row (From, To, a box per text column, a drop-down per parent), pages newest first, sorts by a header and chooses columns. No Add New, Edit, Clone, Delete or form. Each row has a View button that opens a read-only dialog with the whole value of every column, since the grid cuts a long text.
- **Angular, Blazor.** `TS_Component` and `BLZ_Page` write the same screen as for any table with the Add New button and the form left out, the date boxes added, the View button and its read-only dialog in the Actions column, and a spec or tests of their own (`AngularLogSpec`, `BlazorLogTests`).
- **Uno, WinUI3.** `UNO_MasterScreen` and `WinUI3_MasterScreen` leave out Add New, Edit, Clone and Delete, add two boxes, From and To (`yyyy-MM-dd`; WinUI3 ignores text that is not a day, Uno sends it and the API refuses it), and give each row a View button that opens a read-only dialog with a label and the whole value of every column (`DesktopRowView` in Core). The edit dialog and its view model are not written for the table, and neither are their tests.
- **Right-click menu.** Choosing `TSX_LogPage` or `SP_LogIndex` for one table that looks like a log (an integer key, a date-and-time column, nothing that edits it, a log-like name or a level and a message) lists the table in `LogTables` for that run, so the menu writes the page without the project file naming it. The project file is not changed, and every other template still goes by the setting (`LogTablePlan.ForMenuRun`).
- A log table is a plain list, never a master-detail screen (`DatabaseModel.IsDetailMaster`), and the timestamp column shows its time.

## Refused with a reason

A listed table that has no API, a project with `AccessMode=Routines` (the date range is part of the EF search), `ListProtocol=Search` (one box) or a table with no date-and-time column.

## Not covered

The Python and Rust APIs do not serve OData; the menu lists a table for the log page and its index script only, so the read-only API and the screens of the other stacks still need the `LogTables` line; the styles of the View dialog are in the stylesheet essentials of React, Angular and Blazor, and the API essentials file `Apis/CrudApi.cs` is written once, so an older project refreshes them with the replace option before it regenerates.

Checked with `Docs/Verification/Tools/Schemas/log_table.sql`: the API over a scratch SQLite copy (newest first, the range, 405, the export), React, Angular and Blazor in a browser and WinUI3 with UI Automation (a range of two days over 60 rows lists 7), and the generated tests of each. The Python API was run over the same file with rows on both sides of a day boundary and the Rust crate's generated tests were run over it; the generated React, Angular and Blazor tests (View included) pass and the WinUI3 app builds. The View dialogs were not opened in a browser or in the desktop apps.
