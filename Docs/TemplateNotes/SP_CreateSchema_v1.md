# SP_CreateSchema_v1

A create script written from what the database reported about its tables, for the throwaway container the generated API tests start (`ApiTests=true`, `ApiTestContainers=true`). It is written to `sql/CreateSchema.sql` (`OutputRoot=Sql`) for SQL Server, PostgreSQL and MySQL; SQLite needs no container and refuses the template.

The plan includes it only for a project that has `ApiTests` and `ApiTestContainers` and names no `ApiTestSchema` of its own (`ProjectSettings.ImpliedPlanTemplates`). The test fixture then applies `../sql/CreateSchema.sql`, followed by the routines in the SQL folder when `AccessMode` is not `Ef`; a project that names its own scripts keeps them.

## What is in it

`SchemaScript` (Core) writes, in the dialect the model was read from:

- a `CREATE TABLE` per table: every column with its type, identity (`IDENTITY(seed,step)`, `GENERATED BY DEFAULT AS IDENTITY`, `AUTO_INCREMENT`), computed expression, null rule and default, and the primary key;
- `CREATE [UNIQUE] INDEX` for each index other than the primary key's own;
- `CREATE [UNIQUE] INDEX ... [INCLUDE (...)] WHERE ...` for each filtered (SQL Server) or partial (PostgreSQL) index, which the plain index list leaves out because it applies to every row;
- `ALTER TABLE ... ADD CONSTRAINT ... CHECK ...` for every CHECK constraint, whole, whichever columns it names (read as `CheckConstraints` of the table);
- `ALTER TABLE ... ADD CONSTRAINT ... FOREIGN KEY` after every table, with `ON DELETE CASCADE`, `SET NULL`, `SET DEFAULT` or `RESTRICT` as the database has it, so the order of the tables does not matter;
- schemas other than `dbo` and `public`, and PostgreSQL native enum types.

A default is the database's own text. MySQL reports a literal without quotes, so a text or date literal is quoted and a function call is put in parentheses. MySQL names the table alone, because its schema is the database it was read from and the container has its own.

## What is not

Stored routines are not in the script (the routines come from the other templates), so a view or trigger that calls one fails to run in a container made from it. A view that names a table the model does not hold fails to be created.

## Views and triggers

The views follow the tables, each after the views its text names, and the triggers come last. A view is the database's own create statement; PostgreSQL's is rebuilt from its definition, and MySQL's loses the database name in front of its tables, since a container has its own. A PostgreSQL trigger is written with its function (`CREATE OR REPLACE FUNCTION`, then `CREATE TRIGGER`); a trigger that is switched off is created and then disabled (SQL Server, PostgreSQL). SQL Server views and triggers are set apart by `GO` and MySQL trigger bodies are written between `DELIMITER` lines, so the script is run with `sqlcmd` or the `mysql` client, which the test container does. The MySQL test container starts without a binary log, since a login without SUPER cannot create a trigger while it is on. A table with an enabled trigger cannot be saved by the generated Entity Framework code on SQL Server (the database refuses an insert or update with an OUTPUT clause), which is how the real database behaves too.

## Checked

The InvoiceSystem sample of SQL Server, PostgreSQL and MySQL, with no `ApiTestSchema`: every generated test passed over a container filled from this script (and, on SQL Server, in `Ef` mode too). The unit tests (`SchemaScriptTests`) check the text per dialect, the delete rule, the order, the views and triggers and the plan. A table with a view over a view and a trigger was added to the SQL Server, PostgreSQL and MySQL samples and every generated test passed over the containers (SQL Server with the trigger disabled; with it enabled the database refuses the insert, as noted above); the tables were dropped again.
