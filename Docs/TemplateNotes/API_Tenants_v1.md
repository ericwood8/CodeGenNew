# API_Tenants_v1 and the TenantTable, TenantColumn, NoTenantTables and TenantMembership settings

Shared-schema multi-tenancy for the ASP.NET API: one database, one schema, a tenant column on every tenant-owned table, and the rule that a caller reads and writes only the rows of the tenant in their token. It builds on `ApiAuth` and `AccessMode=Ef`; the rule is `TenantPlan` in Core. A schema per tenant or a database per tenant are outside what the generator reads (it reads one schema).

`TenantTable=Tenant` turns it on. **Tenant-owned** is derived, not listed: a table with a NOT NULL whole-number column `TenantId` (`TenantColumn`) that is a foreign key to the tenant table. `NoTenantTables=Country,Currency` leaves out tables that have the column but are shared. The tenant table needs a single whole-number key. The person table (`UserTable`) is normally not tenant-owned: a person can work in several tenants.

## What is generated

| Where | What |
|---|---|
| `CS_DbContext` | `ITenantScope` and `ClaimsTenantScope` (the `tenant` claim of the token), a second constructor that takes the scope, `CurrentTenantId`, and one query filter per tenant-owned entity: `e.TenantId == CurrentTenantId` (together with the soft-delete flag when `SoftDeleteTables` names the table; EF allows one filter per entity). The tenant table is filtered by its own key, so a caller sees only their own tenant; a platform administrator (`ITenantScope.IsPlatform`: the administrator role in no tenant) sees every tenant. A caller in no tenant (`CurrentTenantId` null) sees no tenant-owned row; a context made without the scope sees none either. |
| `CrudApi` / `NameActiveCrudApi` | A tenant-owned table's API says `Tenant => c => c.TenantId`; the base writes the caller's tenant into the row on create **and** on update, whatever the body held, so a row never moves to another tenant. A caller in no tenant is refused (403, `/problems/tenant-required`). Reads, updates and deletes of another tenant's row are 404, since the context never finds it. |
| the tenant table's API | No delete (403, `/problems/tenant-onboarding`): a tenant is switched off with its active flag. Only a platform administrator creates one, by the ordinary create (so the Add form of every front end is the onboarding form) or by the onboarding route; the person who created it becomes its first administrator when they are a row of the user table (`TenantCreator`). |
| `Apis/Tenants.cs` (`API_Tenants`) | `TenantLoginClaims`, `TenantTestSupport` and the routes below. |
| `Auth.cs` (the Jwt essentials) | `LoginRequest` takes an optional `tenantId`; any number of `ILoginClaims` contributors add claims, a role or a tenant to the token (or refuse the sign-in); `AuthUser` answers the tenant. |
| `TableUserDirectory` | Reads the user table without its query filters, since nobody works in a tenant when they sign in (a soft-deleted person still cannot sign in). |

## Who is in which tenant

- **`TenantMembership=EmployeeTenant:EmployeeId:TenantId:Role`** (a table, its person column, its tenant column and optionally a text role column; needs `UserTable`): the person works in the tenant the login asks for (`tenantId` in the login body) or in their first active one. The role of the membership replaces the person's own role in the token, so one person can be an administrator of one tenant and an employee in another. A person who belongs to no tenant signs in to none (a platform administrator); naming a tenant they do not belong to is 403 (`/problems/tenant-not-member`). Inactive tenants (`IsActive` false) are not offered and cannot be signed in to.
- Without a membership table, a user table that is itself tenant-owned (it has the `TenantId` column) puts that tenant into the token.
- `GET /api/auth/tenants` lists the caller's tenants (`{ id, text, role, current }`) and `POST /api/auth/switch-tenant` (`{ "tenantId": 2 }`) answers a new login response with a new token for the same person in another of them (403 when they do not belong to it). Only with a membership table.
- A token of a tenant that has been switched off (its active flag) is answered 401 (`/problems/tenant-inactive`; the front ends sign the person out). The answer for a tenant is remembered ten seconds (`TenantActiveCheck`), so the switch-off takes that long to reach a token in use.

## Onboarding

`POST <tenants>/onboard` with `{ "tenant": { ... the tenant row ... }, "adminId": 7 }` creates the tenant and, with a membership table, a membership of the person `adminId` with `AuthNames.AdminRole` as their role in it, in one transaction (the Python API saves both in one commit; the Rust API checks the person first and removes the tenant again when the membership cannot be saved). Only a **platform administrator** may: the administrator role in a token that has no tenant (the bootstrap administrator, or a person who belongs to no tenant); an administrator inside a tenant gets 403 (`/problems/tenant-onboarding`). A value the database refuses (a missing column, a taken slug, an unknown person) is 400 and nothing is saved. The tenant row is taken as sent, so a created-on stamp the table needs must be in the body. The person who becomes the first administrator is an existing row of the user table (create people with your own routes or script).

## Generated tests

With `ApiTests=true` the fixture finds the first two active tenants of the database (`TenantTestSupport.FirstTenantsAsync`) and the tests work as an administrator of the first, with tokens made from the key of the run (`ClientInTenant`, `PlatformClient`; no sign-in is needed, which also works when the people are rows of the database). Each tenant-owned table gets, in its own test class: another tenant cannot read, change, delete or list a row; a new row belongs to the caller's tenant whatever the body says and an update keeps it; a caller in no tenant sees no row and cannot create one; with `ApiCsv` the export of such a caller holds only the header; with OData the count is 0. `API_Test` writes no class for a Name and IsActive table, so `API_TestTenants` writes the classes of the tenant table (own tenant only, no create, no delete, only a platform administrator onboards) and of the tenant-owned Name and IsActive tables. The tests that need two tenants end inconclusive when the database has fewer than two active ones.

The Python and Rust APIs have generated tests of the same cases, in the same words (`TenantWords`, `NameActiveWords`). `PY_TestTenants` (`PythonTests=true`; not for SQL Server) writes `tests/test_tenants.py` beside the shared `tests/conftest.py`: it replaces `require_user` to work as an administrator of the first or second active tenant (or of none, a platform administrator) and plays every tenant-owned table, every tenant-owned Name and IsActive table and the tenant table. `RS_TestTenants` (`RustTests=true`) writes `tests/api/tenant_support.rs` (the first two active tenants; the tokens of every test of the crate then work in the first, made from the key of the run, so the sign-in of a user table is not needed) and `tests/api/tenant_routes.rs` (the tenant table and the Name and IsActive tables); the isolation cases of the other tenant-owned tables are part of their `RS_Test` module. The text is `PythonTenantTests`, `RustTenantTests` and the shared `TenantTestPlan` in Core. Both also play a token of a tenant that was switched off: the test adds a tenant, works in it with a made token, switches it off with SQL, tells the stack to forget its remembered answer (`forget_tenant`, which `lib.rs` exports for the Rust tests) and expects 401 with `/problems/tenant-inactive`. Both also play the onboarding route (an administrator inside a tenant is refused, a platform administrator onboards a tenant) and, with `TenantHostColumn`, the host case. The first administrator of an onboarded tenant is not played (it needs a person of the user table); `Docs/Verification/Tools` has the check that onboards with one.

## Not covered

The React, Angular and Blazor apps show the tenant's name in the top bar, as a drop-down for a person in several tenants (`Auth` with a `TenantMembership`; a switch loads the screens again). The tenant screen's Add is the onboarding form for a platform administrator (a person who works in no tenant; they see no row of any other table until they switch to a tenant). The sign-in page of the React, Angular, Blazor and Uno apps has a Tenant box (the key of a tenant the person belongs to; empty means the first one; a 403 says the person is not a member or the tenant is switched off); the Uno app shows the tenant in the pane footer of its main page, as a name or, for a person in several tenants, a drop-down (a switch asks the API for a token and makes the menu and the first screen again); the WinUI3 app has no sign-in, so it has neither the box nor the switcher (the calls exist in the API). The Python API (`PY_Tenants`, `app/routes/tenancy.py`, text in Core `PythonTenantWriter`) and the Rust API (`RS_Tenants`, `src/tenancy.rs`, text in Core `RustTenantWriter`) have them: the sign-in takes a `tenantId`, puts the tenant (and the role of the membership) into the token, `GET /api/auth/tenants` and `POST /api/auth/switch-tenant` work, a token of a switched-off tenant is 401, and the router of a tenant-owned table shows only the caller's rows, answers 404 for another tenant's and stamps the caller's tenant on create, update and clone. Both serve a Name and IsActive table (`NameActivePlan`, see `PY_Routes_v1.md` and `RS_Routes_v1.md`), so the tenant table and a tenant-owned Name and IsActive table have their routers: a platform administrator sees every tenant and creates one with the ordinary create, the tenant administrator sees only their own tenant, and the duplicate-name rule compares within the caller's tenant. Not in Python or Rust: `EditableChildren`, soft delete, the CSV routes of a tenant-owned table (left out, since they read every row). In Rust the repository takes a `Tenancy` beside the owner scope, so a table that is both owned and tenant-owned gets both filters. The stacks that read the database directly (a WinUI3 or Uno app over its own context) and anything that bypasses the context (your own raw SQL, a report) know nothing of the filter; `IgnoreQueryFilters()` in your own code removes it too (the soft-delete routes put the tenant back). The places the generator itself writes raw SQL or side tables are covered below. Editable child rows (`EditableChildren`) of a tenant-owned table are stamped with the caller's tenant by the parent's save, whatever the body holds for them (a tenant-owned child needs the `Parent.Child` form of the entry when it also points at the tenant table).

## Where the query filter does not reach

The filter belongs to the EF context, so what the generator writes outside it is handled one by one (in the ASP.NET, Python and Rust APIs unless said otherwise).

- **Dashboard.** Each statement reads a table of the caller's tenant through a derived table, `(SELECT * FROM "Project" WHERE "TenantId" = {tenant}) AS "Project"`, and the API puts the caller's tenant key into the statement before it runs (`NULL` for a caller in no tenant, who is shown nothing). The tenant table is read by its key. A table with no tenant column of its own that points at a tenant-owned one (a junction, an approval side table) is read through its parent: `"ProjectId" IN (SELECT "ProjectId" FROM "Project" WHERE "TenantId" = {tenant})`. The answer is kept a minute per tenant, not for everyone. The people of the user table are not tenant-owned, so their count and names are shown to every tenant, as the Employee screen shows them. The SQL script and the Markdown page that list the widgets (`SP_Dashboard`, `MD_Dashboard`) show the statements for every tenant. The desktop apps read the database directly and are not filtered.
- **Junction tables** (`API_Junction`, `PY_Junction`, `RS_Junction`). The list, link and unlink answer 404 unless the anchor row (and for a link or unlink the target row) is one the caller can see, and the list shows only the target rows of the caller's tenant. A junction table with a tenant column of its own is not detected as a junction table (the column is a third data column).
- **Row approvals** (`API_Approvals`, `PY_Approvals`, `RS_Approvals`). The `<Table>Approval` side table has no tenant column, so a request cycle is the caller's when the row it points at is: another tenant's row cannot be requested, approved, rejected or withdrawn, its history is empty (404 in Python and Rust), and the list of requests waiting for the approver holds only the caller's tenant's. The generated Python and Rust approval tests work in the first active tenant, and their seed row belongs to it.
- **Audit history** (`SP_AuditTable`). The `<Table>_History` table copies every column of the table, the tenant column too, but not its foreign keys, so it is an ordinary table with a key of its own and would be served to every tenant. A table that has the tenant column without a NOT NULL whole-number foreign key to the tenant table therefore stops the generation with a sentence that names it: add the foreign key, leave the table out with `NoApiTables`, or list it in `NoTenantTables` when every tenant may see it.
- **Unique indexes** (`SP_TenantIndex`, `TenantIndexes.sql`). A unique index of a tenant-owned table that leaves the tenant column out (`UNIQUE (Name)`) refuses the second tenant's equal value. The script drops each one and makes it again with the tenant column first, `(TenantId, Name)`, in the dialect of the database (SQL Server and PostgreSQL drop a constraint or an index, whichever the old one is; SQLite cannot drop an index made by a `UNIQUE` constraint in the table definition and says so). It writes nothing when no index needs it, never touches a primary key, and is reviewed and run by you: a duplicate inside one tenant stops the new index. A filtered or partial unique index is not looked at. The duplicate-name rule of a Name and IsActive table compares only within the caller's tenant already.
- **A tenant per host name** (`TenantHostColumn=Slug`; the ASP.NET, Python and Rust APIs). The first label of the host name (`acme` in `acme.example.com`) is compared with that text column of the tenant table (not case sensitive, remembered a minute). A sign-in on the host works in that tenant and is refused (403, `/problems/tenant-host`) when it names another; a person who is not a member, and a person who belongs to no tenant, are refused on a tenant's host. A token that works in one tenant is refused (403, `/problems/tenant-host`) on the host of another, and so is a switch to another tenant. A host that names no tenant (`localhost`, an address, an unknown label) is not restricted, and a platform token is not restricted on any host. Pointing the names at the server (DNS, a wildcard certificate, a proxy that keeps the `Host` header) is yours; the front ends keep their own address and send the token as before.

The generated tests play these cases too, each in a tenant that holds nothing, so the scratch database needs no second tenant and no other test changes what the case sees. **ASP.NET:** `TenantBypassApiTests.cs` (written beside the table classes by `API_TestTenants`) makes a tenant with a platform token and works in it with `ApiFixture.ClientInTenant`. The dashboard test adds a row to a tenant-owned table in the first tenant and checks that the new tenant, and a platform caller, are shown no point and no row of the widgets that read the table. The junction test links a pair in the first tenant and checks that the new tenant cannot list, link or unlink it (or, when only the target is tenant-owned, is not offered the target). The approval test seeds the people and the row like the Python and Rust approval tests, asks as the first tenant's requester and checks that the new tenant's people cannot ask, decide, withdraw or read the history or the waiting list. The host test makes a tenant whose `TenantHostColumn` is a new label and checks the 403 on that host for a token of the first tenant, the 200 for the tenant's own token and a platform token, and the 200 on a host that names no tenant. **Python:** `test_tenants.py` has the dashboard and junction cases and `test_approvals.py` the approval case, in a tenant key no row belongs to (the tests replace `require_user`). **Rust:** `tenant_routes.rs` has the dashboard and junction cases and `approval_routes.rs` the approval case, in a tenant made with a platform token. The Python and Rust APIs do not read host names, so they have no host case. Not in the generated tests: a sign-in and a switch on a tenant's host name (they need a person who belongs to two tenants). `Docs/Verification/Tools/tenant_bypass_check.py` plays all of them against a running API with two tenants and seeded rows (it needs a scratch schema with a junction table and an approval side table; its header says how to start it). Checked with `Docs/Verification/Tools/Schemas/tenants.sql` (tenants, people, memberships, an organization table and a project table): the generated API tests over a SQLite copy, a sign-in, switch and onboarding battery written for the scratch project, and the whole generated test suite of the InvoiceSystem databases with `TenantTable=Tenant` on SQL Server, PostgreSQL and MySQL.
