# WinUI3_Test_v1 and WinUI3_EssentialTests_v1

MSTest tests of the view models the WinUI3 dialogs are written with, in a test project beside the WinUI3 app. `DesktopTests=true` in the project file adds both to a whole-project run (or name `WinUI3_Test` in `PlanAlso` and run the `Tests` essentials group of the WinUI3 stack). The files go to `OutputWinUI3Tests` (default `<ProjectName>.WinUI3.Tests`); the template config says `OutputRoot=WinUI3Tests`. `codegen generate --test` runs `dotnet test` on that project when `DesktopTests=true` and `TestWinUI3` says nothing.

- **The project is a plain `net10.0` one** (`WinUI3_EssentialTests`, essentials group `Tests`, written only with `DesktopTests=true`): it compiles the app's own files as linked files (ViewModels, Data, Entities and Repositories), so the tests run on any machine with the .NET SDK, with no window, no WinUI and no device. Two platform types a view model touches are small stand-ins in `PlatformShims.cs` (`Visibility` and the WinRT `CurrencyFormatter`), so the tests do not judge how a number is shown in a grid.
- **`TestDb` is the generated context over an in-memory SQLite database made with `EnsureCreated`, with foreign keys unchecked so a row can be saved without its parents. The project references the SQLite provider besides the app's own provider. A row version column (SQL Server `rowversion`) starts with the same eight bytes in the database and in the sample row, so an update finds the row it expects. A context with provider-specific SQL (a default such as `getdate()`, a computed column) may not create on SQLite: then the test project needs its own `TestDb`, which the Tests group does not overwrite.**
- **What a class tests** (`<Table>DetailViewModelTests.cs`, or `<Table>DetailMasterViewModelTests.cs` for a table with child tables), over an in-memory SQLite database: a new row with nothing filled in is refused with the first required field's sentence; a row opened and saved unchanged is saved with every value it had; and each rule the form has refuses a spoiled value after a valid row was opened: a text shape (email, phone, web address, ...), a date later than today (`NotFutureDateColumns`), an end date before its start (`DatePairs`), a number that is not whole.
- **Where the cases come from:** `DesktopTestPlan` in Core decides them from the rules `DesktopFormCode` writes the view model from, and `DesktopTestCode` writes the class, so WinUI3 and Uno test the same things. The row is made from the same sample values as the API tests (`ApiSampleValues`).
- **Not tested:** how the dialog looks, the child grids' sorting, the typed key (a new row's key box is open and an existing row's is locked), the guards and the editable child rows' lines; a dialog is still checked by driving the app.
