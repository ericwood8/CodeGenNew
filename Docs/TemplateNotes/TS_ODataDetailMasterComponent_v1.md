# TS_ODataDetailMasterComponent_v1

The OData form of the master-detail Angular screen: four files in `components/<table>-odata/` over the table's `<Table>ODataService`, with the route `<table>-odata` and the menu entry `<Table> (OData)` (after the REST ones in `app.routes.ts`). The REST master-detail screen is not touched.

`TS_ODataDetailMasterComponent_v1.tt` is a stub: its config says `Base=TS_DetailMasterComponent_v1.tt` and `Variant=OData` (see `TS_ODataComponent_v1.md`). The OData form has everything the plain OData screen has (`TS_ODataComponent_v1.md`): the several-column sort with order badges, the filter row, the slim grid with the row read whole on Edit, dates shown in UTC, Clone through the REST route. The form and the child grids under it are the REST screen's.

**The child grids.** A child that is served as OData too (`ODataPlan.ServesByName`: `OData=true`, in `ODataTables` or the list is blank, not refused by `NoApiTables`, the user table, gates, guards or `Dtos`, and no owned tables in the project) reads its rows from its entity set, filtered by the parent's key: `GET odata/<child set>?$filter=<fk> eq <id>&$orderby=<child key>`, following the next links. The REST screen reads the whole child table and filters it in the browser. A child that is not served, or has no single key, keeps the REST route. The child's own page (Edit on a child row) and Delete are still the REST ones. (The generated entities have no child collection property, so `$expand` of the children is not used: the child set is asked for the rows that point at the parent.)

**Not offered:** a table whose form edits child lists (`EditableChildren`) has no OData screen and is not served as OData at all (`ODataPlan` refuses it: the OData routes do not save the lists). A name/active master (a department and its teams) has its screen like the REST one (the name box, "active only", no paging), with the child grids read from the child entity set filtered by the parent key.

Written only for the master-detail tables the project serves as OData (the template writes nothing for another table, so a whole-project run can include it for every master-detail table). Opt in with `OData=true` or `PlanAlso=TS_ODataDetailMasterComponent`. Needs the `OData` essentials group and `TS_ODataService`.

**Checked:** generated for a scratch copy of the SQL Server InvoiceSystem (Customer, Item, SalesInvoice and the monthly summary are master-detail there), 101 specs, and in the browser: the Sales Invoice OData screen (50 rows by `$count`, the filter row, Edit reading `odata/salesinvoices/1` and the child grid `odata/salesinvoicelines?$filter=salesInvoiceId eq 1&$orderby=lineId` with its formatted columns) and the Customer OData screen (a text filter `contains(tolower(customerName),'ame')` gave 3 rows, an edit saved by PUT and read back from the database, the child grid asked `odata/customeritems?$filter=customerId eq 28`). A production `ng build` of that project with 12 OData screens added passed the compile but exceeded the sample's 1 MB initial-bundle budget (1.12 MB): the routes import every screen eagerly.
