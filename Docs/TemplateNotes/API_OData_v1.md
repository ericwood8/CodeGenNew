# API_OData_v1

`Apis/OData.cs`: the tables the project selects, served as OData v4 under `/odata`, next to the REST routes under `/api`, which stay exactly as they are. Whole-database. Opt in with `OData=true` (the plan writes the file; `Program.cs` calls `builder.Services.AddGeneratedOData()` and `app.MapODataEndpoints()`, and the generated API project references `Microsoft.AspNetCore.OData` 9.5.0) or `PlanAlso=API_OData` (then add the package and the two calls yourself). Regenerate the Program essentials with `--replace` in a project made before the flag existed.

**Which tables.** `ODataTables=Customer,Product` names them; blank or `*` is every table with a CRUD API (a single int, uniqueidentifier or text key, not an enum) or the API of a name/active table (a NOT NULL `Name` and `IsActive`). The rule is `ODataPlan` in Core. A table the routes cannot make as safe as the REST routes is left out and named in a comment at the top of `OData.cs`: the user table, `NoApiTables`, a table listed in `OwnedTables` that has no owner column and no owned parent, a table whose form edits child lists (`EditableChildren`), and, with `Dtos=true`, every table (the REST API hides columns the entity shows). Navigation properties that point at a table that is not served are removed from the model, so `$expand` cannot reach it.

**With `ApiAuth=true`: owner scoping, gates and guards.** Every `/odata` route needs a token, like the REST routes. A table whose rows belong to a person (`OwnedTables`, its own owner column or through its parent, `OwnedTable` in Core) gets a generated `<Table>ODataRules` class and the routes do what `CrudApi` does: the list holds only the rows of the owners the `IOwnerScope` allows (the administrator role sees every owner), a row of another owner is 403 `not-your-row` by key (404 when there is none) for a read, put, patch and delete, a create goes under an owner the caller may act for (a caller who may act for one owner and left the owner blank creates the row for that owner), and a put or patch cannot hand the row to anyone else. No navigation leads into a table that is scoped, so `$expand`, `$filter` and `$orderby` cannot read another person's row through a parent. A table with `ChangeGates` or `GuardedColumns` runs its `<Table>Gates.CheckAsync` before a create, put or patch (409 `change-not-allowed`, 403 `column-not-yours`, the stamps written); the screens read `GET /api/<route>/guards`, which the OData service calls through the REST route. The roles are the ones the REST routes know: the administrator role in `IOwnerScope`, the user table's manager flag in a guard. `WriteRoles` and `TableWriteRoles` (item 110) apply to the writes of both routes: a role the table's rule does not list (the administrator role is always listed) gets 403 `role-not-allowed` on POST, PUT, PATCH and DELETE; reads stay open unless `ReadRoles` or `TableReadRoles` lists roles: then the list and the read by key answer 403 `role-not-allowed` to another role (the list refuses inside its handler, because the group's query filter cannot pass a problem result on).

**Reads.** `GET /odata/<set>` takes `$filter`, `$orderby` (several columns, and a parent's column such as `countryRef/name`), `$top`, `$skip`, `$count=true`, `$select` and `$expand` (with nested `$select`, `$filter` and `$orderby`). The answer is `{ "@odata.context", "@odata.count", "value": [...], "@odata.nextLink" }`. The set name is the REST route's name (`/api/customers` and `/odata/customers`), property names are the ones the REST JSON uses. The list reads the context (`context.Set<T>().AsNoTracking()`), so search and sort code of the repositories and the stored procedures is not used. `GET /odata/<set>/{key}` and `GET /odata/<set>(key)` (text keys as `('CA')`) answer one row as plain JSON, the same body the REST route gives.

**Limits** (always written, from the project settings): `ODataMaxTop` (100), `ODataPageSize` (25; a longer answer carries `@odata.nextLink`), `ODataExpandDepth` (2) and 100 nodes in one query. A bad query (an unknown property, `$top` over the limit, `$expand` too deep) answers `400` problem details of type `/problems/invalid-request`; the REST problem types are used for the writes.

**Writes.** `POST /odata/<set>` (201 with `Location`; an identity key is ignored; a text key must be present, 400 `key-required`, and new, 409 `duplicate-key`), `PUT /odata/<set>/{key}` (204; a key in the body that differs from the address is 400), `PATCH /odata/<set>/{key}` (a partial body, 200 with the row; the key, identity, computed and version columns cannot be changed, 400 `change-not-allowed`; an unknown property or a value of the wrong type is 400) and `DELETE` (204; a row in use answers the same problem as the REST route). A refused database write answers through `ApiProblems.ToResult`, as the REST routes do. With `ApiValidation=true` the table's validator runs on POST, PUT and PATCH.

**Columns no caller may set.** `ODataEndpoints` is a partial class with one hook, `static partial void Stamp<T>(DbContext context, T row, bool isNew)`, called before a row is added (`isNew` true) and after a put or a patch changed it. The generated code sets nothing (like `CrudApi.Stamp`); a project that stamps who and when writes the body in its own file: `public static partial class ODataEndpoints { static partial void Stamp<T>(DbContext context, T row, bool isNew) where T : class { ... } }`.

**Name/active tables.** A table with a Name and an IsActive column keeps the REST routes’ rules: a generated `<Table>ODataRules` checks before every create, put and patch that the name is not blank (400 `name-required`), trims it and refuses a second active row with the same name (409 `duplicate-name`, "An active row named ‘X’ already exists."; an inactive row may repeat a name unless the database has a unique index, which answers `duplicate-value`). Such a table is never scoped to a person, as in the REST routes. Its list is the plain entity set (every row, no search endpoint; the OData screen reads all the pages).

**Dates.** A `date` column is written as `Edm.Date` (`"2026-03-01"`); other date columns are `Edm.DateTimeOffset` in UTC (`...Z`). A filter may use `2026-03-01` for a date and `2026-03-01T00:00:00Z` for a date and time.

**With `ApiAuth=true`** the group needs a token like every other route; the write roles are above.

**Not offered:** `$batch` (the package's batching does not honor `dependsOn`), `$search`, `$apply` (grouping: the package runs the GROUP BY but cannot write the grouped answer from a minimal API, a 500, so the route answers 400 `invalid-request` for it), delta queries. `$metadata` and the service document are at `/odata/$metadata` and `/odata/$document`.

**Checked with real sign-ins (`Docs/Verification/Test-ODataScoping.js`, 35 checks):** a scratch copy of InvoiceSystem with `ApiAuth`, the user table, `OwnedTables=SalesInvoice:CustomerId` (the invoice lines are owned through the invoice) and the gate and guard of `API_Gates_v1.md`, three people (an administrator, a manager, an employee): each person lists only their customer's invoices and lines (a `$filter` that matches everything, a larger page and another order do not widen it), a read by key of another's row is 403, a create for another customer is 403, put, patch, hand-over and delete of another's row are 403 and change nothing, `$expand` or `$filter` into a scoped table is 400, the gate refuses moving an invoice of a customer in Bad Standing (409) until a manager sets Ignore Bad Status, the guarded column is refused for the employee (403) and stamped for the manager, and the user table has no OData route. Generated without the scoping and the two rules, 21 of the 35 fail.

**Checked on the generated file:** generated for a scratch copy of the SQL Server InvoiceSystem database (11 tables served), built, run and called with curl, with `ApiValidation=true` and with `ApiAuth=true` (401 without a token on `/odata`, `$metadata` and `/api` alike): the reads above including nested `$expand` and a parent-column sort, create (201), patch (a key change is 400 `change-not-allowed`, a wrong type 400), put (a key mismatch is 400), delete (a row in use is 409 `in-use`, a missing parent is 400), the validator's messages on POST, PUT and PATCH, and the REST route of the same table still answering. Sign-in as a real user and owner scoping were not exercised (owned tables are refused). Known small gaps: the service document's `@odata.context` has no `/odata` in it; a single row by key has no `@odata.context` and prints unloaded navigation properties as `null`.

**Checked in the first scratch proof:** the same registration was run in a scratch project against SQL Server, PostgreSQL and MySQL (the Oracle provider): filters, `contains(tolower(...))`, parent-column sort, paging with a next link, nested `$expand`, int and text keys in both forms, create, patch, put, delete and delete in use; see spec item 114.
