# WinUI3_Auth_v1

The sign-in of the WinUI3 app: `Repositories/DesktopSignIn.cs`, `Views/LoginView.xaml` and `Views/LoginView.xaml.cs`. Whole-database, written only for a project with `Auth=true`, the `WinUI3` stack, `ApiAuth=true` and a `UserTable` (the plan adds it). The WinUI3 app reads the database itself and has no API to sign in to, so the app checks the password against the user table, with the hash the API writes (`PasswordService`, `pbkdf2-sha256$iterations$salt$hash`; `set-password` writes it). It is a check in the client: the API is where the rules are enforced.

- **`DesktopSignIn.SignInAsync(context, userName, password, tenantId)`** reads the user table without its query filters, checks the password, works out the role the way the API does (the role column, a yes/no column as the two `UserRoleWhenTrue` and `UserRoleWhenFalse` roles, `UserAdminColumn` as the `AuthAdminRole`) and answers a `SignedInUser`. A refused sign-in throws `SignInException` with `SignInProblem.WrongPassword`, `TooManyTries` (five wrong passwords for one name in a minute) or `NotMember`.
- **`LoginView`** is the sign-in the main window shows until someone signs in, with the sentences "The user name or password is not right.", "Too many tries. Wait a minute and try again." and "Could not sign in right now." (the same as the Uno sign-in page).
- **`MainWindow`** (`WinUI3_EssentialMainWindow`, written for this project) shows `LoginView` first, then the menu of the screens, the person's name and Sign out in the pane footer. A signed-in person is `DesktopCaller.Name` for the guards and approvals when the project has them. Sign out forgets the person and shows the sign-in again.

## Tenants

With `TenantTable` the context filters every tenant-owned table by `DesktopTenantScope.Current`, the one scope of the app. The window sets it when someone signs in or switches tenant; every context the pages make (`new <Context>()`, which the dashboard, the junction pages and the approvals use too) reads it. The scope is written into the context file next to `ITenantScope`; the API's `ClaimsTenantScope` is written into `Apis/Tenants.cs`, so the context file holds no ASP.NET type.

- **Tenant box.** With `TenantMembership` or a tenant column on the user table, `LoginView` has a Tenant box (the key of a tenant the person belongs to; empty means the first one). `NotMember` says "You are not a member of that tenant, or it is switched off."
- **Name and switcher.** With `TenantMembership` the pane footer shows the tenant (a name for a person in one tenant, a drop-down for a person in several). A switch makes a new context and shows the first screen again. `DesktopSignIn.TenantsAsync` lists the active tenants of a person and `SwitchAsync` answers the person in another one.
- **Roles.** A membership role replaces the person's own role in that tenant (`SignedInUser.Role`; `OwnRole` keeps the person's own). A person who belongs to no tenant and has the administrator role is a platform administrator (`SignedInUser.IsPlatform`): the tenant table shows every tenant, every other table stays empty until they work in a tenant.
- **Writes.** The context stamps the signed-in tenant on a new tenant-owned row and never moves a row to another tenant on an update (`StampTenant`), the same as the API does. Without a tenant (a platform administrator) nothing is stamped, so adding a row there fails in the database; they work in a tenant to add rows.
- **Tenant table.** The tenant table's own screen lists the tenants the scope reaches. Add New and Clone show only to a platform administrator, and a tenant added there makes that administrator its first administrator (a membership row with the `AuthAdminRole`, found by the user name they signed in with), as the API does for a tenant created through its route. Because that person now belongs to a tenant, their next sign-in without a tenant box picks it. Onboarding with a first administrator who is a new person, with a password, is the API's `POST <tenants>/onboard`; this app has no such dialog.

## Roles

With `ReadRoles`, `TableReadRoles`, `WriteRoles` or `TableWriteRoles` the screens follow the role of the signed-in person (`DesktopSession.User`, set when someone signs in or switches tenant, so a membership role counts). The menu lists only the screens the role may read (the junction pages by the read roles of the junction table), and Add New, Edit, Clone and Delete, the single-row Save and a junction page's Edit links show only to the roles that may write the table, the same rule the Uno screens use. A role that may read nothing sees an empty window. The roles only change what the screens show: the app reads the database with its own login, so the API is where they are enforced.

Limits: the person is not kept between runs (no token on disk); the approvals page and the dashboard are not limited by the roles; the password of a person is set with the API's `set-password` command, not in this app.
