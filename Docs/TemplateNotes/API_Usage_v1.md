# API_Usage_v1 and the UsageTables and UsageLimits settings

```
UsageTables=UsageEvent:Kind:Quantity:OccurredOn
UsageLimits=api_calls,emails
UsageRollup=UsageMonthly:UsageMonth:Quantity
UsageRollupDays=60
```

An append-only ledger of billable events (an API call, an email sent, a gigabyte stored), written by the server and summed per tenant, kind and month. It builds on the tenants (`TenantTable`, `API_Tenants_v1.md`) and, for a limit, on the plans (`SubscriptionTable`, `PlanLimitTable`, `API_Subscriptions_v1.md`). The rule is `UsagePlan` in Core, the text `UsageWriter` (ASP.NET), `PythonUsageWriter` and `RustUsageWriter`. It needs `ApiAuth`, `AccessMode=Ef` and `TenantTable`.

## The table

A table and, after colons, its kind, quantity and occurred-on columns. A part that is left out is found by name:

| Column | What it holds | Found by |
|---|---|---|
| tenant | The tenant the event is billed to: the table's `TenantColumn`, a NOT NULL whole number that is a foreign key to the tenant table | the tenant rules |
| kind | What was used (`api_calls`, `emails`): NOT NULL text | a name that starts or ends with `Kind`, `Metric`, `Meter`, `EventType`, `Event`, `Feature` or `Type` |
| quantity | How many units: a NOT NULL whole number or decimal (3.5 gigabytes). Optional: without it every event is one unit | `Quantity`, `Qty`, `Units`, `Amount`, `Count` or `Value` |
| occurred on | When it was used: a NOT NULL date and time (`DateTime`, not an offset) | a name that starts or ends with `Occurred`, `Recorded`, `Timestamp`, `EventDate`, `EventTime`, `CreatedOn`, `CreatedAt`, `LoggedOn` or `At`; with several, the one that starts with `Occurred` |

The table needs a single whole-number key. A table that lacks something fails the run with the list of what it lacks. A column of the table that no route manages and that cannot be NULL gets an example value when an event is recorded by a route or a generated test; a table with such a column that is a foreign key (or a type the generator does not fill) gets the recorder but no record route and no generated tests.

## What the table does not get

No list and edit screen, no ordinary CRUD API and no TypeScript model in any front end: it is treated as a `NoApiTables` table without being listed there. Nothing edits or deletes an event: the generated tests prove that `PUT`, `PATCH` and `DELETE` of an event are not routes. `ArchiveTables=UsageEvent:90:delete` ages the table by when the event occurred.

## What is generated (`Apis/Usage.cs`)

One static class per table (`UsageEventUsage`), registered by `API_Registration` as `UsageApi.Register`.

- **`RecordAsync(context, tenant, kind, quantity = 1, occurredOn = null, set = null)`** is the only writer of an event. The event is written (the ledger is what happened), unless the project says `UsageRefuse=true` (see below). The answer, `Recorded(Id, Used, Allowed, Over)`, says what the month (UTC) holds of the kind now, what the tenant's plan allows (null: unlimited) and whether the tenant is over. `set` fills the other columns. `RemainingAsync` says how many more units may be used before the plan is passed: the owner's code calls it before the work a unit pays for. `UsedThisMonthAsync` is the sum the plan limit reads.
- **`GET /api/usageevents`** (an administrator of a tenant, or a platform administrator with `?tenantId=`): `[{ month: "2026-11", kind, quantity, events }]`, newest month first, the units and the number of events of each kind in each month (UTC); with `UsageRollup` it also lists the months that were rolled up (their `events` is 0). `?kind=` keeps one kind, `?from=` (inclusive) and `?to=` (exclusive) bound the dates. A caller who is not an administrator gets 403, and a tenant's administrator never reads another tenant's rows.
- **`POST /api/usageevents`** (a platform administrator: the administrator role, working in no tenant), body `{ tenantId, kind, quantity?, occurredOn? }`: a service that meters outside this API records an event. 201 with the `Recorded` answer; 400 for no tenant, a blank or too long kind, a quantity that is not above zero or a fraction for a whole-number ledger; 404 for an unknown tenant. A person inside a tenant gets 403.

## Plan limits (`UsageLimits`)

`UsageLimits=api_calls,emails` names plan limits (rows of `PlanLimitTable`, `LimitKey`) that are counted from the month's events instead of from the rows of a table: each name is a kind of a usage table. With several usage tables a name counts the events of the first table listed in `UsageTables`, or of the table written after a colon (`UsageLimits=api_calls,emails,hits:ApiCall`): a limit is judged by the events of its own table only, and the subscription view counts the same way. It needs `SubscriptionTable` and `PlanLimitTable`, and a name cannot also be in `PlanLimits`. The subscription view (`GET /api/subscription`) lists the limit with what the plan allows and what the month holds (`used`), the list of plans shows what each allows, and `Recorded.Over` is true when the month passes what the plan allows. No row, or a NULL value, is unlimited. A limit never refuses the event or a request by itself: the ledger records what happened, and the owner's code decides (with `RemainingAsync` before the work, or `Over` after it). A kind that no plan limits is never over.

## Refusing past the limit (`UsageRefuse`)

`UsageRefuse=true` (it needs `UsageLimits`) makes a plan limit refuse. `RecordAsync` reads the month before it writes: when the units already used plus the units of the new event pass what the plan allows (reaching it exactly is allowed), nothing is written and the answer carries `Refused = true` (Python `"refused": True`, Rust `"refused": true`) with the `Used` and `Allowed` it saw, so the owner's code decides what to tell the person. The record route answers 402 with the same plan-limit problem as a create past a plan limit (`/problems/plan-limit`, "Plan limit reached"). A kind no plan limits, a tenant with no plan row and a plan with no limit for the kind are never refused, and an event dated in an earlier month is judged against nothing (the limit is the month's). The check and the write hold a lock on the tenant, so requests at the same moment cannot both pass: ASP.NET `UsageGate` (a transaction that locks the tenant row: `UPDLOCK` on SQL Server, `FOR UPDATE` on PostgreSQL and MySQL, a process lock on SQLite, with the database put in write-ahead mode as the API starts: in the default journal a request that only reads can make the commit of an event fail with "database is locked", a 500), Python `_gate` (the same), Rust a semaphore plus an advisory lock (`pg_advisory_lock`, MySQL `GET_LOCK`; a process lock on SQLite). Requests of other tenants do not wait for each other. Without the setting the event is always written and `Over` says the tenant is over.

## Rolling old events up (`UsageRollup`)

`UsageRollup=UsageMonthly:UsageMonth:Quantity` names the monthly total table (a table and optionally its month and quantity columns and, as a fourth part, the usage table it totals; its tenant and kind columns are found like the ledger's). With several usage tables give one entry for each (`UsageTables=UsageEvent,ApiCall` with `UsageRollup=UsageMonthly,ApiCallMonthly`): an entry goes to the table at the same place in `UsageTables`, or to the table it names as its fourth part (`ApiCallMonthly:UsageMonth:Quantity:ApiCall`), a table with no entry has no roll-up, and two tables never share a monthly table. Each table with an entry gets its own `RollUpAsync` and `POST <route>/roll-up` and `UsageRollupDays` (default 60) says how old an event must be. The monthly table holds one row per tenant, kind and month (a unique key on the three is what the generator expects), its key is a single whole number, and it has no other column that cannot be NULL and has no default. Like the ledger it gets no ordinary API or screen.

- **`RollUpAsync(context, before = null)`** (the owner's scheduler calls it) adds the events before the first day of the month that contains "today minus `UsageRollupDays`" into the monthly totals and removes them: a thousand events at a time, each batch in one transaction that adds each tenant, kind and month to its monthly row (or makes the row) and removes exactly the events it counted, so an event that arrives while it runs is never lost. `before` can only move the day earlier: it is never later than the start of this month, so a month the plan limit still reads is never rolled. It answers `{ events, months }`.
- **`POST /api/usageevents/roll-up?before=2019-04-01`** (a platform administrator) is the same call for a service that does not run inside the API; a person inside a tenant gets 403.
- **`UsageRollupHours=24`** makes the API call the roll-up of every table that has one on its own, every 24 hours (ASP.NET `UsageRollupSchedule.Start` from `UsageApi`, Python `roll_up_every` started by the lifespan of `main.py`, Rust `start_roll_up` started by `serve`). The first run is one interval after the start, not at the start, and a failed run is logged and tried again at the next interval. Run it in one instance of the API only: two instances can read the same batch and total it twice. Without the setting nothing runs the roll-up by itself.
- The summary reads both tables: the months that were rolled up appear with their total and no events, a month with both (a roll-up that stopped halfway through a month, or an event that arrived late) adds the two, and the kind and date filters apply to the monthly totals: a rolled up month has no days, so it is kept only when the whole month lies between From and Before (a day that cuts into it leaves it out).

## The other stacks

`PY_Usage` (`app/routes/usage.py`) and `RS_Usage` (`src/routes/usage.rs`) write the same routes with the same sentences and answers (`UsageWords`), `record_usage`, `used_this_month` and `remaining`, and the same reading of the plan limit (`subscriptions.py` and `subscriptions.rs` ask the ledger for a usage limit). Each is written over a table with no model: a SQLAlchemy `Table` and sqlx statements. With several usage tables each table gets its routes and a plan limit goes to the table it belongs to (see `UsageLimits`).

## The usage page (`TSX_Usage`, `TS_Usage`, `BLZ_Usage`, `UNO_Usage`, `WinUI3_Usage`)

A project that signs in (`Auth`, `ApiAuth`) and has `TenantTable` gets a page for each usage table in the menu of the administrator role: a table of the months and kinds (month, kind, quantity, events), newest month first, with a column for each month above the table (oldest first, as tall as the units of all the kinds shown, so it follows the Kind, From and Before boxes) and a bar for each line (a `meter` on the web, a `ProgressBar` on the desktop; the longest bar is the largest quantity shown), and three boxes with a Show button: Kind (`?kind=`), From (the first day shown, `?from=`) and Before (the first day left out, `?to=`). The web pages use date boxes; the desktop pages take a day written year-month-day and say so when it is not one. A month that was rolled up has no days, so it is shown only when the whole month lies between From and Before. The months that were rolled up show their total and no events. The route of the page is the table's name in kebab case (`usage-event`), its title the plural of the table's name. A platform administrator (no tenant) gets the sentence that says to work in a tenant. The text of every stack is in `UsageScreens`, `UsageWebCode` and `UsageDesktopCode` in Core; the templates only choose the file names. React and Angular also get a test of the page (`vitest`).

- React, Angular, Blazor and Uno read `GET` of the table's route.
- WinUI3 reads the database through the app's own context for the tenant the person works in: it adds up the events and, for the first usage table, the monthly totals of `UsageRollup`, and shows the same table. It needs the desktop sign-in with tenants.

## Generated tests

With `ApiTests` and `ApiAuth`, `API_TestUsage` writes `<Table>UsageApiTests.cs`: a call without a sign-in is a 401, a role that is not the administrator's is a 403, the summary adds the events per month and kind (and the kind and date filters work, newest month first), another tenant's events are not in it, a platform administrator names the tenant to read, a platform administrator records usage and a person inside a tenant may not (with the 400s and the 404), and nothing edits or deletes an event. Each test adds events of its own and removes them again. `Docs/Verification/Tools/usage_check.py <base url> <sqlite file>` plays the routes, the plan limit and the roll-up against a running ASP.NET, Python or Rust API over `Schemas/usage.sql` (whole-number units) or `Schemas/usage_decimal.sql` (decimal units): the over flag, a kind exactly at its limit, a kind no plan limits, an earlier month that is not counted, the subscription view, raising the limit, and the roll-up with its second run and its clamp to this month. The generated tests also ran over SQL Server (the `UsageEvent` and `UsageMonthly` tables of `InvoiceSystem_test`, with a decimal quantity, a foreign key and a default on the occurred-on column), PostgreSQL and MySQL (`Schemas/usage_postgres.sql` and `Schemas/usage_mysql.sql` add the same two tables and rows to the standing `InvoiceSystem` and `invoicesystem` databases).

With `PythonTests` (not on SQL Server) `PY_TestUsage` writes `tests/test_usage_<table>.py` for each usage ledger, and with `RustTests` `RS_TestUsage` writes `tests/api/usage_<table>.rs`: the same cases and sentences as the ASP.NET tests (no token is a 401, a role that is not the administrator's a 403, the summary per month and kind with the kind and date filters, another tenant's events, the platform administrator who names the tenant and records usage with the 400s, the 404 and the fraction a whole-number ledger refuses, the roll-up when the ledger has a monthly table and units, and no edit or delete route). A ledger needs a record route, because the tests record their events through it. The Python tests remove what they recorded (they work in a scratch copy of the SQLite file, or the database named by `<PROJECT>_TEST_CONNECTION`); every Rust test works in a database of its own. With `UsageLimits` on a ledger that counts units, on a database the subscription tests can put a plan in with SQL (`SubscriptionTable`, not SQL Server), they also make a tenant on a plan of their own and play the plan limit: the answer says when the tenant passes its plan and the subscription view shows what is used, and with `UsageRefuse` a request past the plan is a 402 that writes nothing, reaching the limit exactly is allowed, an event of an earlier month is judged against nothing, raising the limit lifts the refusal, and thirty requests at the same moment let exactly the limit through. `usage_check.py`, `usage_refuse_check.py`, `usage_two_check.py`, `usage_limit_table_check.py` and `usage_race_check.py` still play the same against a running API.

## Not covered

Generated Python and Rust tests of a limit that belongs to a second usage table or of a ledger with no units column (the check scripts play the second table), an idempotency key (a retried call to the record route records twice), a month other than the calendar month of UTC, a refusal that holds across several instances of the API on SQLite (its lock is per process), and a schedule that is safe in several instances of the API at once (run it in one). `Docs/Verification/Tools/usage_race_check.py` plays many requests at once and `usage_limit_table_check.py` plays limits that belong to different tables.
