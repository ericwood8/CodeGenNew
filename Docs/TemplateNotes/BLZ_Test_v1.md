# BLZ_Test_v1 and BLZ_EssentialTests_v1

bUnit tests of the Blazor pages, in a test project beside the Blazor app. `BlazorTests=true` in the project file adds both to a whole-project run (or name `BLZ_Test` in `PlanAlso` and run the `Tests` essentials group of the Blazor stack). The files go to their own folder, `OutputBlazorTests` (default `<ProjectName>.Blazor.Tests`); the template config says `OutputRoot=BlazorTests`. `codegen generate --test` runs `dotnet test` on that project when `BlazorTests=true` and `TestBlazor` says nothing.

- **What a class tests** (`<Table>PageTests.cs`, over the page `BLZ_Page` writes): the heading; a row the server returns is in the page; the Edit button of that row opens the dialog; the dialog holds the row's value and Save sends the row in a PUT; and `?edit=<key>` opens that row (the page reads it by its key). The row is `GridTestRow`'s, the same one the React and Angular tests use, written as JSON (`GridTestRow.Json`); a table with no column to recognise a row by has the heading test only.
- **No server and no database:** `FakeApi` is the `HttpMessageHandler` behind the page's `HttpClient`. A read answers the text given for the end of its path (an empty list when none), a search answers `FakeApi.Page(rows, count)`, a write answers 204 and every call is kept in `Requests`.
- **Auth=true:** `PageTestContext` registers the app's `AuthSession` and authentication state, and each test signs in first (`SignIn(role)`) as a role that may read and write the table (the first of `WriteRoles`, else of `ReadRoles`). A role the table does not allow shows no Edit button, so the Edit tests fail for it.
- **The test project** (`BLZ_EssentialTests`, essentials group `Tests`, written only with `BlazorTests=true`): MSTest 4, bUnit 2, a project reference to the Blazor app, `FakeApi.cs` and `PageTestContext.cs` (the bUnit context every class derives from: the clients over `FakeApi`, a loose JS runtime for the column and sort choices the pages keep in the browser).
- **Which tables:** the ones `BLZ_Page` writes a page for; any other table is refused with the reason.
- **The OData page** (`BLZ_ODataPage`) has a class of its own in the same file (`<Table>ODataPageTests`) when the table is served as OData: the list is answered as `{ value, @odata.count }` at `/odata/<set>`, and the page reads the row again by its key (`/odata/<set>/<key>`) when Edit is pressed.
- **Child grids:** a master-detail page has one test per read-only child grid. The child table answers one row that belongs to the row being edited (`ChildTestRow` in Core builds it), the test presses Edit and expects one row in the dialog's grids. An OData page reads a child served as OData from `/odata/<child set>`, any other child from its REST route. An editable child (`EditableChildren`) is not tested.
- **Junction pages** (`BLZ_JunctionTest`, one class per junction table): the drop-down lists the anchor rows, choosing one fills Available and Selected, a picked row moves with a POST to `.../junction/link` and Remove all unlinks with a POST to `.../junction/unlink`.
- **The dashboard** (`DashboardPageTests`, written by `BLZ_EssentialTests` when the project has a dashboard): a count card, a money card in the project's currency, a bar list and the recent rows from a stand-in `/api/dashboard`, the sentence for an empty dashboard and the one for a failed load.
- **Not done:** the grids' sorting, filtering, paging and Columns list on the Blazor pages, a Save refused by the API, Delete and Clone, and the layout and menu.
