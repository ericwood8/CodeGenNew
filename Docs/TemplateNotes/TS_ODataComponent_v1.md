# TS_ODataComponent_v1

The OData form of the Angular screen: four files in `components/<table>-odata/` (css, html, spec and TypeScript) over the table's `<Table>ODataService`, with its own route (`<table>-odata`), selector, saved-sort key and menu entry (`<Table> (OData)`, after the REST ones in `app.routes.ts`). The REST screen is not touched.

`TS_ODataComponent_v1.tt` is a stub. Its config says `Base=TS_Component_v1.tt` and `Variant=OData`: the engine runs the text of `TS_Component_v1.tt` with the template parameter `Variant` set to `OData` (a stub is how one template text serves two forms without a copy). `TS_Component` writes the OData names, the OData service and an OData spec when it sees the variant; with no variant its output is byte for byte what it was.

What is the same as the REST screen: the fields, the form pages, the grid columns, the captions, the drop-downs (read from the parents' REST lookup routes), the validation, `PagedCrudScreen`. What differs:
- the list is `GET odata/<set>?$count=true&$top=&$skip=&$filter=&$orderby=`, read as `{ value, '@odata.count' }`;
- a date and time comes with a `Z`, so the grid's date pipe shows it in UTC (the column has no zone; its stored value is the day shown). A date box fills from the first ten characters;
- Clone calls the REST route (OData has none).

Written only for the tables the project serves as OData and that have a plain screen: a master-detail table has `TS_ODataDetailMasterComponent` (the template writes nothing for a table that is not served, so a whole-project run can include it for every table). Opt in with `OData=true` or `PlanAlso=TS_ODataComponent`. Needs the `OData` essentials group (`odata-query.ts`, `odata-crud.service.ts`) and the service from `TS_ODataService`; the dev proxy and the container's nginx forward `/odata` when `OData=true`.

**Checked:** generated for a scratch copy of the SQL Server InvoiceSystem, built (`ng build`), its 79 specs run, and clicked in the browser: the first page, sort by a plain column and by a parent's display column (`$orderby=customer/accountNumber,customerItemId`), the next page, edit (a date changed, read back from the database), add, clone (through the REST route), delete, and on the sales invoice lines the search boxes (`contains(tolower(quantityUm),'o''b')`, a text with a quote stays one literal) and Clear.

**What the OData screen has that the REST screen does not** (the screen extends `ODataPagedScreen`, `components/odata-screen.ts`):
- **Several-column sort.** A click sorts by the column (again: flips it). Shift-click adds the column as the next sort (again: flips it, once more: takes it out). A column in a several-column sort shows its place (1, 2, ...) in a small badge; the header's tooltip says how. The list is kept between visits in the same place as the single sort (`gridSort:<screen>`, a list). The server gets `$orderby=item/itemNumber,purchasedDate desc,customerItemId` (the sorts in order, then the default order).
- **Filter row** under the headers, a control per column by its kind (`ODataFilterFields` in Core, one rule for every stack): text (contains, ignoring case), number and date (from and to; the last day is included), yes/no (Any, Yes, No), a foreign key (a drop-down of the parent's rows) and a column whose values the database lists (a drop-down). A column that can be empty also gets an "empty" check box (it wins over the other controls of its column). Long text, binary and guid columns have no control. Enter in a box searches; Search and Clear are the last cell of the row. The one search box of `ListProtocol=Search` stays above the grid.
- **A slim grid.** The page asks (`$select`) for the columns the grid shows (the person's choice in the Columns list, see `TS_Component_v1.md`) and the key only; Edit reads the row whole (`GET odata/<set>/<key>`) before the form opens, so a column the grid does not show is in the form.

**Lazy routes.** `TS_Screens` lists an OData screen with `load: () => import('./components/<table>-odata/<table>-odata.component').then((m) => m.<Table>ODataComponent)` and maps it to `loadComponent`, so each OData screen is its own chunk, downloaded when its route is first opened; the menu entry (`path`, `label`) is the same. Without OData screens the routes file is unchanged. A production build of the InvoiceSystem sample with six OData screens added kept the initial bundle at 829 kB (the REST-only size; eager imports made it 1.12 MB and tripped the default 1 MB error budget) and put the screens in lazy chunks of 11 to 64 kB; opening an OData route in the browser loaded two new chunks and drew the screen.

**A name/active table** gets the REST screen’s own form over its OData service: a name box and an "active only" check box that narrow the list on the page, no paging and no sort, no filter row. The list is every row of the entity set (`getAll` follows the next links), the add, edit and delete are the same calls, and a duplicate or blank name is refused in the API’s own words (“An active row named ‘X’ already exists.”) with the form kept open.
