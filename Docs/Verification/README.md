# Verification harness

A build and a unit test cannot see a blank drop-down, a number box that takes a value the database refuses, or a dialog that never closes. This folder holds the tooling for checking a change in a **running** app, so a check recorded as done can be run again.

| File | What it does |
|---|---|
| `ScratchDatabase.ps1` | Makes or drops `<name>_scratch`, a throwaway copy of a database: SQL Server by backup and restore (Windows authentication), PostgreSQL by `CREATE DATABASE ... TEMPLATE`, MySQL by copying the tables. Passwords come from the environment (`PGPASSWORD`, `MYSQL_PWD`), never a parameter. The login needs the right to create a database (MySQL: a login limited to one database cannot). |
| `TestDatabases/` | The standing test database `InvoiceSystem_test` (SQL Server): `Regenerate-InvoiceSystemTest.ps1` restores the real database over it, applies the routines that write with the value rules on and runs a seed of tagged `ZZ` fixture rows (stored values that break a rule, rows in use, rows to delete, a last page of one). See its README. |
| `UiAutomation.psm1` | A small Windows UI Automation module for WinUI3 apps: `Start-App`, `Find-Name`, `Find-Like`, `Find-Type`, `Wait-Name`, `Invoke-El`, `Select-El`, `Set-Text`, `List-Names`, `Assert-That`, `Stop-App`. |
| `Test-AppDialogs.ps1` | A worked click-through of the CodeGenNew app (the Project settings dialog and the Essentials dialog): PASS / FAIL lines and an exit code. |
| `Test-ApiCrud.ps1` | Starts a generated API on a spare port against a scratch database and walks one route through POST, GET, PUT, list and DELETE. |
| `Test-WinUI3Paging.ps1` | Drives a generated WinUI3 list page through its paging bar on a scratch SQL Server copy: seeds extra rows so the last page holds one row, picks a page size of 10, walks to the last page, deletes that row through the confirmation dialog and checks that the grid steps back (no "Page 7 of 6"), then checks "Nothing found." for a search with no match. It points the app at the copy by editing `appsettings.json` next to the exe and puts it back. Defaults to the InvoiceSystem sample; build it for x64 first. Checked to fail when the step-back is removed from the view model. |
| `Test-OpenApiRoutes.ps1` | Checks the generated `openapi.yaml` against the running API: every documented GET answers 200, every `PUT /{id}` 400, and the schema's properties are in a real row's JSON. Apply the generated SQL to the scratch database first. |
| `Test-ApiSignIn.py` | The sign-in of a generated Python or Rust API (`ApiAuth=true`, `UserTable`, `OwnedTables`): 55 checks over HTTP with real sign-ins (the 401s, the hash never shown, the user-table guards, the owner scope, a child through its parent, the throttle). The passwords come from the environment. |
| `Test-SearchHostileText.py` | The generated `SP_Search` routine of SQL Server, PostgreSQL or MySQL (`sqlserver`, `postgres`, `mysql`): creates a scratch table, generates and applies the routine and feeds it wildcards, quotes, an injection attempt, unknown sort names and paging edges (30 checks), then drops what it made. `--prove-failure` removes the escaping first so the wildcard checks fail. Passwords come from `PGPASSWORD` and `MYSQL_PWD`. |
| `Test-GatedChanges.py` | The change gate and the guarded column of a generated ASP.NET API (`ChangeGates`, `GuardedColumns`) over HTTP with real sign-ins of an employee, a manager and an administrator, on a SCRATCH copy of InvoiceSystem: 33 checks (who may change the column, the refused and allowed moves, the stamp, a clone, the CSV import). Passwords come from `EMPLOYEE_PASSWORD`, `MANAGER_PASSWORD` and `ADMIN_PASSWORD`. Against an API generated without the rules it fails 20 checks, which shows it can. |
| `Prepare-ODataScoping.js`, `Test-ODataScoping.js` | The owner scoping, the change gate and the guarded column of the generated **OData** routes (`OData=true` with `ApiAuth`): three real sign-ins, 39 checks (lists, keys, writes, hand-over, `$expand` and `$filter` into a scoped table, the gate, the guard, and the Columns list: a `$select` of columns the grid does not start with, the REST search of an owned table refused and a REST read answering whole rows only for one's own). Node, over a scratch copy of InvoiceSystem; passwords derive from `TEST_SEED`. |
| `Test-WriteRoles.js` | `WriteRoles` and `TableWriteRoles` on the REST and OData routes with three real sign-ins (administrator, manager, employee) on a scratch InvoiceSystem copy prepared by `Prepare-ODataScoping.js`: 37 checks (a read rule on one table, writes refused with 403 `role-not-allowed`, a manager and the administrator write, a table that lists only the administrator, a table with an empty entry). Generate with `WriteRoles=Manager`, `TableWriteRoles=Item:Administrator;CustomerStatus:` and `TableReadRoles=Item:Administrator`; passwords derive from `TEST_SEED`. |
| `Test-PythonDashboard.py` | The read-role filter of the generated **Python dashboard** (`PY_Dashboard`): three real sign-ins, 17 checks (the administrator and the manager see the widgets of a table limited to managers, the employee does not, also on a cached answer, and the strip of that table is empty). |
| `Test-ApiRoles.py` | `ReadRoles`, `WriteRoles` and `TableWriteRoles` on a generated **Python or Rust** API (`ApiAuth`, `UserTable=Employee`): three real sign-ins (administrator, manager, employee), 19 checks (a table only the administrator writes, a table only a manager reads, the lookup open). The passwords come from `ADMIN_PASSWORD`, `EMPLOYEE_PASSWORD` and `MANAGER_PASSWORD`. |
| `Test-RustBuild.ps1` | The Rust stack: generates the crate of a PostgreSQL, MySQL or SQLite database with `codegen generate --essentials`, compiles it with `cargo build` (in a Visual Studio developer environment that has the C++ libraries) and runs `Test-ApiCrud.ps1` against the binary (`-Executable`). Needs a Rust toolchain. `Test-OpenApiRoutes.ps1` takes `-Executable` too. |
| `Test-SqliteStack.ps1` | The SQLite counterpart of the API check: generates the API of a SQLite file with `codegen generate`, builds it and runs `Test-ApiCrud.ps1` against a scratch copy of the file. No server is needed. |
| `Test-AngularVersion.ps1` | Generates the Angular app of a project for one Angular version (`-Version 18` to `22`) into a scratch folder, runs `npm install`, `ng build` and `ng test` (Karma with ChromeHeadless up to 20, Vitest from 21) and exits 1 on the first failure. It reads the database, never writes to it. |
| `Test-FrontEndPages.py` | The generated React, Angular, Blazor WebAssembly or Uno browser app in a real browser (`--stack react|angular|blazor|uno`; Playwright with the installed Chrome or Edge; `pip install playwright`, no browser download). Generates the master_detail sample as API and the front end over a throwaway SQLite file, starts the API and the front end (Vite, `ng serve` or `dotnet run`; the Uno app needs `wasm-tools` and is driven through its accessibility page by focus and keys, because it draws on a canvas and a click lands on nothing), walks the Region screen (an empty form refused, add, search, edit, clone, delete) and asks the API after each step what the database holds. `--out <folder>` reuses a generated project; `--prove-failure` aborts the browser's POST so the checks must fail. Stops what it started. |
| `Tools/` | Python scripts for the repeated steps of a template change: a scratch SQLite project, the comparison of the output with HEAD. See `Tools/README.md`. |
| `Browser.md` | Snippets for driving and reading a React / Angular page from the browser's console. |
| `Recipes/` | The steps per stack: `Api.md`, `React.md`, `Angular.md`, `WinUI3.md`. |

## A typical run

```powershell
$env:PGPASSWORD = '<your password>'          # in your own shell only
.\ScratchDatabase.ps1 -Provider PostgreSql -Source MyDatabase -User dev_login
.\Test-ApiCrud.ps1 -ApiProject C:\MySample\My.Api -Route /api/customers `
    -ConnectionString 'Host=localhost;Port=5432;Database=MyDatabase_scratch;Username=dev_login' `
    -Body '{"accountNumber":"A-1","customerName":"Test","customerStatusId":1,"isTaxable":false}' -IdProperty customerId
.\Test-AppDialogs.ps1
.\ScratchDatabase.ps1 -Provider PostgreSql -Source MyDatabase -User dev_login -Drop
```

Every script stops what it started in a `finally` block and exits with 1 when a check fails, so they can be chained. Checks that need the app connected to a database (the Generate All dialog, the screens of a generated app) follow the same pattern: copy the database, start the app with the copy's connection, drive it with `UiAutomation.psm1`, drop the copy.
