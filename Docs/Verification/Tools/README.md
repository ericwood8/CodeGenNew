# Verification tools

Small Python scripts for the steps that are repeated whenever a template or a Core helper changes. They need Python 3, the .NET SDK and a built CLI (`dotnet build CodeGenNew.Cli`, or `--build-cli`). They hold no passwords or machine names.

| Script | Use |
|---|---|
| `new_scratch_project.py` | Builds a throwaway SQLite database from a schema file (`Schemas/plain.sql`, `Schemas/master_detail.sql`, `Schemas/junction.sql` with a many-to-many table and a cascading key, `Schemas/field_limits.sql` with a month, a money amount and a birth date and one row already outside the limits, `Schemas/approvals.sql` with an employee table and a time sheet for RowApprovals (apply the script `SP_ApprovalTable` writes, then generate again), `Schemas/approvers.sql` (the same with the side table and an `Approver` table for `ApproverTable=Approver:EmployeeId,TableName`), `Schemas/log_table.sql` with an `ErrorLog` (a timestamp, a level, a user and a message) beside an ordinary table, for `LogTables=ErrorLog`, `Schemas/inbound.sql` with a `WebhookEvent` (an event id, a source, a processed time) and an `ErrorReport` (a processed flag) for `InboundTables=WebhookEvent,ErrorReport:Payload` (play the generated tests with the environment variable `INBOUND_WEBHOOK_SECRET` set), `Schemas/tokens.sql` with a `Session`, a `PasswordReset`, an `EmailCode` and a `RefreshToken` table (run with `matrix_check.py --schema tokens` and the settings in the schema header; `Schemas/tokens_postgres.sql` and `Schemas/tokens_mysql.sql` add `Employee` and `AuthToken` to the standing PostgreSQL and MySQL InvoiceSystem databases), `Schemas/queue_archive.sql` with an `ErrorLog` and its `ErrorLogArchive` and a `JobQueue` holding pending, done and failed rows, for `QueueTables=JobQueue` and `ArchiveTables=ErrorLog:90,JobQueue:30:delete`, `Schemas/gated_changes.sql` with employees, customers with a guarded flag and invoices for ChangeGates and GuardedColumns, `Schemas/name_active_shapes.sql` with a name and active table that is soft deleted and one that is effective dated, `Schemas/desktop_rules.sql` with an email, a phone, a not-future date, a start and end date, a whole number and a text-keyed child, or your own), writes a project file for it in the CLI's `Projects` folder and generates into a temp folder. `--set Key=Value` adds project settings, `--stack` picks the stacks. |
| `regenerate_samples.sh` | Runs every `C:\Samples\InvoiceSystem<Name>\docs\Regenerate.sh` (all but WinUI3, or the names given) with `REPLACE=1 QUICK=1` and prints each one's summary and exit code; start it with `run_logged.py` and `run_in_background`. The database password comes from `CG_PW` and only reaches the child scripts as `PGPASSWORD` and `MYSQL_PWD`. |
| `container_run.py` | Generates the API and its tests for an existing SQL Server, PostgreSQL or MySQL database with `ApiTestContainers` and no `ApiTestSchema`, then runs them over a container filled from the create script written from the catalog (needs Docker). The password comes from `PGPASSWORD` or `MYSQL_PWD`. Use it to prove a change to the create script or the container fixture. |
| `compare_with_head.py` | Generates with the working tree's templates, puts the committed copy of every changed template back, generates again and lists the files that differ (`--diff` shows the lines). Run it with the scratch project to prove that a change moved only what it should. |
| `crlf_test_run.py` | Runs the unit tests on a CRLF copy of the working tree, the way the Windows CI runner checks the repository out (`--filter` for a few tests, `--keep` keeps the copy). A test that looks for `"\n"` in generated text passes with LF files and fails on the runner; this shows it before the push. |
| `ef_read_all.py` | Reads every table of a generated app (`--app Output/X.App`) through its generated DbContext in a throwaway console project (Entities, Data, Repositories only) and prints `FAIL <DbSet>: ...` per table that cannot be read, ending `tables ok=N fail=M`. Finds what a build cannot: a relationship EF cannot build, a NULL in a column EF made required, a missing column. SQL Server; read only. |
| `tenant_bypass_check.py` | Plays the dashboard, a junction table (the list of its rows, the list of every link and link and unlink), the row approvals and the host name of a tenant against a running multi-tenant API over a scratch copy of `Schemas/tenants_bypass.sql`: `python tenant_bypass_check.py http://localhost:5080 <sqlite file> [dashboard,junction,approvals,host]`. It writes test password hashes into the copy. Works against the ASP.NET, Python and Rust APIs. The generated test suites hold the same cases in a tenant that holds nothing; this script also plays the sign-in and the switch on a tenant's host name. |
| `tenant_onboard_check.py` | Plays `POST <tenants>/onboard` (a member is refused, an unknown first administrator is a 400 and saves nothing, a platform administrator onboards a tenant with a first administrator who exists, with one who is a new person with a password, who then signs in, and without one; a short password, a taken user name and both ways of naming the person are a 400) against a running multi-tenant API over the same scratch copy: `python tenant_onboard_check.py http://localhost:5080 <sqlite file>`. Run `tenant_bypass_check.py` first, it writes the test password hashes. |

| `matrix_check.py` | Generates a scratch project once and builds or tests each generated stack, one line per cell (PASS, FAIL with the first error lines, or SKIP with the reason): `python matrix_check.py Shop --schema master_detail --stack api,python,rust,blazor --set ApiTests=true --set PythonTests=true`. A typical check of a template change:

```bash
python new_scratch_project.py Shop --schema master_detail --stack api,react --set Dtos=true
python compare_with_head.py --project Shop --db <database path printed above> --stack api,react --diff
```

Then run the tests of the generated front end with `run_frontend_tests.py` from the general tools folder, passing the generated app folder.

Angular needs `--set AngularVersion=22` for Vitest on jsdom. Tables need five or more columns to get a screen. A change in Core code is in both runs of `compare_with_head.py`: compare that with a `git worktree` of HEAD.
